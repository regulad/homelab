# bpg/proxmox 0.122.0 from the registry, and PepperCord's MongoDB data on a disk of its own (2026-11-16)

- The 0.118.0 build planned a replacement of any container that gains a `mount_point`, as the whole block was ForceNew; `prevent_destroy` stopped the plan. 0.122.0 updates mount points in place and then reboots the container. It also carries every Ceph resource the build was made for, so `tofu/gonkputer` now pins the registry's release. `tofu.rc` keeps the mirror after `direct {}`. The shared `.terraform` keeps each installed version side by side, so other checkouts on the old lock file went on working.
- Two of 0.119–0.122's changes showed in the plan. Containers' root disks now default to `replicate = true`, and the 16 adopted containers have `replicate=0` live, so their disks state `false`; the other containers already read as true. VMs now read `usb4` and higher, so aboriginal's CyberPower UPS, live as `usb4` (`mapping=CPS`), would have been detached until its `usb` block was declared.
- An apply to `tofu/gonkputer` makes alock record its commit for every host in the root's inventory, not only the guests it changed.
- cordpepperer and peppercord each have a 4 GB `rbd` mount point at Podman's default volume path, `/var/lib/containers/storage/volumes`, with `backup = true`. MongoDB's data is off the 8 GB root disk, and the compose file PepperCord's README links to is unchanged. The new ext4 comes with a `lost+found` that an unprivileged container sees as `nobody:nogroup`, and a 0755 root, which was set to Podman's 0700.
- The move ran with the unit disabled, not only stopped. The provider's reboot, and the watchdog's, then started nothing on the empty disk. podman-compose's `down` had removed the containers, so podman-restart.service had nothing to start at boot. The volumes were renamed aside, the apply mounted the empty disk in their place, and a `cp -a` and `diff -rq` brought them back. The document counts matched before and after.
- The watchdog (Uptime Kuma's notification to prodingus's webhookd) rebooted each container once its stack had been down two to three minutes: cordpepperer at 04:44:10, in the middle of a `diff` run inside it, and peppercord at 04:49:09. It fired once per outage. On peppercord, the apply waited for that reboot, and the copy went through without one.
