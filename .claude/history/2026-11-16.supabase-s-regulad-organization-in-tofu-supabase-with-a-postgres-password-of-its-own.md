# Supabase's regulad organization in tofu/supabase, with a postgres password of its own (2026-11-16)

- Supabase's scoped personal access tokens (`sbp_fc…`) limit a token to chosen organizations or projects and grant read or read-write per capability; access cannot be changed after creation, and a token expires within a year. `homelab-tofu` is scoped to the `regulad` organization. The provider has no resource for an organization itself.
- doppelganger's `DATABASE_URL` (transaction pooler, port 6543) and `DIRECT_URL` (`db.<ref>.supabase.co:5432`) log in as a `prisma` role, not `postgres`, and their values are double-quoted in the env file, which Compose strips. `supabase_project` requires the `postgres` password, which Supabase never returns and nothing held, so a new one was generated into SOPS and the adoption set it. The provider changes the password in place; it never replaces the project for it.
- `supabase_settings` reads back only the keys each JSON group declares, and neither reads nor sends a group left null. An import reads every key, so the first plan after it shows an update that trims state; that update sends only the declared keys, at their live values. The API returns no secrets (Google's client secret, a captcha secret, SMTP passwords), so they are never read back.
- Config generation writes every resource but errors on `supabase_project`'s `database_password`, which nothing can generate; the file is still written.
- The project's Auth sends with Supabase's built-in email: its auth config has no `smtp_*` keys.
