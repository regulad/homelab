# pam_rssh's debs are to go to one Nexus APT repository per suite (2026-11-18)

- **FIXME: one APT repository per suite is a workaround.** Nexus should hold pam_rssh's debs in one APT repository with a distribution per suite, as a Debian archive does. Nexus's hosted APT repositories take a single distribution, the one `dists/{distribution}/Release` path its API describes, and its API offers no APT group to merge several. The upstream request is https://github.com/sonatype/nexus-public/issues/309 ("Multiple distributions in the same APT repository", open since 2024-01-05). https://github.com/sonatype/nexus-public/pull/1038 (ikus060, 2026-08-07, rebased onto 3.94.1) adds a distribution and component to each upload, with metadata per distribution; it was unmerged on 2026-11-18. Once it, or something like it, reaches Community Edition, fold the per-suite repositories into one. pam_rssh gives every distribution's build the same file name (`pam-rssh_1.2.2-1_amd64.deb`), so first check that the merged feature pools them apart.
- **Nexus can't be patched with a plugin:** "The OSGi bundle capability has been removed from the Nexus Repository as of version 3.78.0" (Sonatype's bundle-development page). The APT format is EPL-1.0 in `sonatype/nexus-public` (`public/common/components/formats/nexus-repository-apt`), but that tree builds Nexus Repository Core. The Community Edition the homelab runs is Sonatype's own binary, with formats Core lacks, Docker and NuGet among them. A forked APT format would mean running a second, self-built Nexus. The YUM format is not in the public tree.
- **YUM can be one repository:** a hosted YUM repository's `repodataDepth` gives each `<channel>/<target>/<arch>` directory its own repodata, and Sonatype's YUM page shows a depth-3 hosted repository behind a group. Nexus signs only a proxy's or a group's metadata (`yumSigning`), never a hosted repository's, and never the RPMs, so clients take `repo_gpgcheck=1` with `gpgcheck=0` for pam_rssh's unsigned RPMs.
- **Tested with throwaway repositories:** a depth-3 hosted repository (`stable/el9/x86_64`, `stable/fc44/x86_64`) behind a group signing with a throwaway ed25519 key. The group served `repodata/repomd.xml` and its `.asc` about a minute after the uploads, and `gpg --verify` passed. In disposable containers, AlmaLinux 9's dnf 4 and Fedora 44's dnf 5 installed `pam-rssh` with the key. With another key, dnf 4 refused with "repomd.xml GPG signature verification error: Bad GPG signature" and dnf 5 with "Signing key not found". The repositories were deleted afterwards.
- **pam_rssh's releases,** on 2026-11-18: `v1.2.1` holds Ubuntu 22.04, 24.04 and 26.04 debs versioned `1.2.0-1`; `v1.2.2-rc1` and `v1.2.2-rc2`, neither marked a pre-release on GitHub, both build `1.2.2-1`, under asset names that changed between them. rc2 builds for Debian bookworm and trixie, Ubuntu 22.04, 24.04 and 26.04, Fedora 42, 43 and 44, and Enterprise Linux 9 and 10, each for amd64 and arm64. A tag with a SemVer pre-release part counts as a pre-release, for testing repositories, whatever GitHub's flag says.
- **Jenkins had no build capacity:** 2.580.2 with 112 plugins installed by hand, neither Configuration as Code nor Job DSL among them; 0 executors on the controller, no agents and no clouds since the Docker cloud on `tinker` went. Its one item, the `regulad` GitHub Organization Folder, held no jobs and scanned with a username and password credential, `regulad`, described "github".
