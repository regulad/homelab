# Jenkins's builds run on agents of rootless Podman beside it, as jenkins-agents (2026-11-19)

- **Ubuntu 26.04's AppArmor profile for pasta kills it inside a Proxmox container.** In the container's AppArmor policy namespace, the profile denies pasta's `file_mmap` of its own binary: its exec fails with EACCES, then it dies of SIGSEGV. The denials are logged in prodingus's `/var/log/audit/audit.log`, not in either kernel log. The profile has no `local/` include to amend, so the `podman` role disables it (`/etc/apparmor.d/disable/`) and unloads it (`apparmor_parser -R`); pasta stays within the container's own confinement. Launchpad bug 2173698, libvirt's passt backend on 26.04, and the bugs it links, such as 2154379, report other denials by the passt profiles.
- **Rootless Podman in an unprivileged container:** a user's subordinate IDs must lie among the container's 65,536, and useradd allocates them from 100000, so the role replaces them (1002, count 64532, short of nobody's 65534). pasta needs `/dev/net/tun`, which `device_passthrough` gives the container; set to mode 0660, it shows 0666 inside. The bpg provider reboots a started container for a change of its memory or device passthrough, 49 s here.
- **Root reaches a user's service manager as `<user>@.host`.** The Proxmox containers' `ansible_become: false` outranks a task's `become_user`, so `systemctl --user` ran as root, and the user's bus refuses root ("Operation not permitted … consider using --machine=<user>@.host"). `systemctl --user --machine=<user>@.host` works as root, without machined (systemd 259). Likewise, the podman CLI run through `runuser` has no systemd session: it falls back to cgroupfs, and `podman exec` into a container its API service started fails writing `cgroup.procs`. Inspect such containers through the API socket instead; the jenkins container has Python but no curl.
- **Through the Docker API, a container without a network gets Podman's bridge, which is IPv4 alone:** `podman`, 10.88.0.0/16, with only link-local IPv6. `NetworkMode: pasta`, the docker-plugin template's `network`, gives the container's GUA and ULA instead, and `host.containers.internal`, 169.254.1.2, still reaches the controller's port 8080.
- **The docker-plugin registers an inbound agent's node itself.** In the script console, `cloud.provision(new Cloud.CloudState(Label.get('podman'), 0), 1)` alone starts an agent that connects; cloud-stats then warns "No activity tracked", as NodeProvisioner never recorded it. `RemotingDiagnostics.executeGroovy(script, computer.channel)` runs code on the agent. DockerOnce removes an idle agent, node and container, after 10 minutes. The console's Groovy has no `withCloseable`.
- **The inbound-agent image's entry point reads `JENKINS_WEB_SOCKET` and `JENKINS_AGENT_WORKDIR`.** Without the second, remoting has no work directory and warns that it uses the legacy JAR cache.
- **Rootless Podman pulls through the system's registry mirrors:** the agents' image came through Nexus's `docker-io` proxy, in 8 s.
- **ansible-generated's inventory reads OpenTofu state with the shell's AWS settings.** Once its hour-long cache expires, an `AWS_ENDPOINT_URL` or `AWS_PROFILE` exported for something else sends it to the wrong S3 endpoint (NoSuchBucket). Run `ansible-playbook` under `sops exec-env tofu/shared/backend.sops.env`, with the stage's `bin/` first in `PATH` for its `tofu-<root>` wrappers.
