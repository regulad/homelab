# doppelgangerhq.com: on the tailnet, with webhookd behind Tailscale Serve for doppelganger's pipeline (2026-11-16)

- regulad/tailscale-acls has `tag:ci-client-doppelganger`, for doppelganger's GitHub Actions runners, and `tag:ci-server-doppelganger`, for doppelgangerhq.com, with a grant from the first to the second on tcp:8108 alone. The policy's tests also deny each pipeline the other's webhookd.
- `POST https://api.tailscale.com/api/v2/tailnet/-/acl/validate`, with the policy's HuJSON as the body (`Content-Type: application/hujson`), validates it and runs its tests without applying it. A pass answers `{}`; a failing test still answers HTTP 200, with `"message":"test(s) failed"` and each failure in the body, so read the body rather than the status.
- GitHub's immutable OIDC subject (`repo:<owner>@<owner id>/<repo>@<repo id>:ref:...`) has no plugin in the Settings app (repository-settings/app) or in safe-settings, and neither project has an issue asking for one. It is set once per repository with `PUT repos/<owner>/<repo>/actions/oidc/customization/sub`, `use_default=true` and `use_immutable_subject=true` (201); `GET` on the same path shows the resulting `sub_claim_prefix`.
- Tailscale's keys API shows a federated identity's issuer, subject, audience, tags and scopes: list the IDs with `GET /api/v2/tailnet/-/keys?all=true`, then `GET /api/v2/tailnet/-/keys/<id>`. The client ID is the key's ID, and its audience is `api.tailscale.com/<id>`.
- The tailscale role used to join with `tailscale up --auth-key --advertise-tags` alone, so a new node ran on the client's defaults until the next task applied `tailscale_settings`. accept-dns's default, on, sent every lookup on doppelgangerhq.com (`~.` on tailscale0) to 100.100.100.100, which forwards to pihole and pihole2, unreachable there with accept_routes off. Its DNS failed for about four minutes, until `tailscale set --accept-dns=false`, the web app's lookups of its Supabase pooler and Sentry included: dockerd's embedded resolver forwards containers' queries to resolved's stub, 127.0.0.53, so the host's DNS is its containers'.
  - sudo, unable to resolve the host's own name, took longer than Ansible's 12 s privilege-escalation timeout, which Ansible reports as the host being UNREACHABLE, and mailed "problem parsing sudoers": that mail is about the name lookup, not the sudoers files, which `visudo -c` passed.
  - PepperCord's hosts went through the same window without harm, as Ansible reaches them through `pct`.
  - The role now passes `tailscale up` the declared settings it takes too (tailscale_node's `up_flags`). On Tailscale 1.104.7 that is all of tailscale_node's settings but auto_update, relay_server_port and relay_server_static_endpoints, which only `tailscale set` takes.
- Tailscale names a new node after the OS hostname's first label: doppelgangerhq.com joined as `doppelgangerhq`. `tailscale_settings.hostname: doppelgangerhq-com` renames it, the dot spelled as a dash.
- doppelgangerhq.com resolves through Oracle's 169.254.169.254, from DHCP; the host stays on it (`accept_dns: false`).
- webhookd is upstream's arm64 build here (VM.Standard.A1.Flex), the archive mail pins. Its hook starts `doppelganger-update.service`, the Docker stack's equivalent of podman-auto-update, which its daily timer also starts.
