# Sentry's regulad organization in tofu/sentry, its DSNs delivered to Synapse, PepperCord and doppelganger (2026-11-16)

- Providers for the last SaaS accounts: Stripe publishes `stripe/stripe` (0.x; its repository has no licence file, so OpenTofu's registry shows no docs for it; resources import, and its own docs advise `-parallelism` of 2 to 5). Supabase publishes `supabase/supabase`. Its `supabase_project` reads no `database_password` back, so the first apply after an import writes the configured password to the live database. Sentry publishes none; `jianyuan/sentry`, which it sponsors, is the one in use. OneSignal has no provider; its account holds one app, Doppelganger, with only seeded segments and templates.
- OpenTofu's registry holds no signing key for `jianyuan/sentry`, so `tofu init` skips its signature check.
- The token is an internal integration's, from its Tokens section; the integration's client secret only signs webhooks. Every `organizations/<org>/` endpoint answered 403 until the integration had Organization: Read; the existing token took the new permission without being regenerated.
- The provider requires a team on every project. doppelganger and the three pheidippides projects had none, so the adoption put them in `regulad`.
- `-generate-config-out` writes no configuration for `for_each` import blocks. What it generated set the project filters' lists to `[]`, which the provider rejects, and every other optional project and key setting: left out, they plan as no-ops, so only name, slug, team and platform are declared.
- `sentry_alert` imports as `<org>/<id>`, the ID in the alert's `monitors/alerts/` URL, and needs `monitor_ids`: each project's default issue-stream monitor, read through `sentry_project_issue_stream_monitor`. The high-priority triggers pass through `legacy_trigger_conditions`. Seer's "pull requests are ready" alerts use `seer_activity_trigger`, which the provider cannot express, so they stay unmanaged.
- `default_key = false` makes the provider delete every key named `Default`. In 0.16.0 it does so only while creating a project; an earlier build did on update too (jianyuan/terraform-provider-sentry#603).
- The worktree guard refuses sourcing `prepare.sh`. With its inputs already decrypted, `sops exec-env tofu/shared/backend.sops.env` around `sops exec-env tofu/sentry/provider.sops.env` gives `tofu` the same environment; Ansible needs only the first, with `ansible-generated/bin` on `PATH` for the inventory's `tofu-<root>` wrappers.
- doppelganger's app builds its DSN in, in `apps/web/sentry.dsn.ts`, for the browser, server and edge alike; the `NEXT_PUBLIC_SENTRY_DSN` now in `web.env` waits on the app reading it. PepperCord's `PEPPERCORD_SENTRY_DSN` replaces the DSN built into the bot, which was already the peppercord project's.
- A check-mode run shows no change from Compose for a changed `env_file`, as check mode leaves the old file in place; the real run recreates the service.
- PepperCord's `.env`, one SOPS string per mirror, became `peppercord_env` in group_vars, with each mirror's prefix in its host_vars and its token alone in SOPS. `PEPPERCORD_HOME_SERVER` and the MOTD settings were dropped, retired on the production bot.
