# warlockctl, warlock-extcap and warlock-installer get Sentry projects beside warlock's (2026-11-21)

- **An organization token reaches every project in its organization, later ones included:** `from_rpc_auth` (`src/sentry/auth/access.py`) gives a token with no user, whose organization matches, `ApiBackedOrganizationGlobalAccess`, over all of the organization's active projects. The debug-file endpoints (`DebugFilesEndpoint`, `DifAssembleEndpoint`) use `ProjectReleasePermission`, and the organization's releases `OrganizationReleasePermission`, both of which take `org:ci` for GET, POST and PUT. So a new project needs no change to a repository's existing `SENTRY_AUTH_TOKEN`.
- **Checking a token's reach without writing:** with the token, `projects/<org>/<slug>/files/dsyms/` and `organizations/<org>/releases/?project=<id>` answer 200 for a project it can upload to and release in, while `organizations/<org>/` answers 403, as an `org:ci` token should.
- **Warlock's build uploads only the daemon's PDB:** `.github/workflows/build.yml` runs `sentry-cli debug-files upload -p warlock` over `debug-files/warlock.pdb` alone, and calls the daemon the one program that reports to Sentry, so the other programs' symbols reach their projects only once the build uploads their PDBs with `-p` for each. Its one `windows-latest` build job builds warlock, warlockctl (whose package builds warlock-extcap too) and `warlock-msi-ca`, the MSI's custom action DLL, so every program built there shares warlock's two checkout paths.
