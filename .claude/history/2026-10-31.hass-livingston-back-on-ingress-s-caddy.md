# hass-livingston.regulad.xyz back, on ingress's Caddy (2026-10-31)

- Its route had been the deleted `aboriginal` tunnel's `http://localhost:8123`. It is now a DNS-only CNAME to `ingress.regulad.xyz`, as ingress's other sites are; arawi's split-horizon RPZ rewrites that CNAME target for LAN clients, so the name needs no entry of its own there.
- Home Assistant 2026.10 keeps its HTTP settings in `.storage/http`, as a `stable` and a `pending` config. Its first start migrated `configuration.yaml`'s `http:` block once (`yaml_migration_done`), and later starts ignore the YAML, raising the repair `yaml_still_present_after_migration` while the block stays; the YAML stops working in 2027.2. The UI and the WebSocket command `http/config/set` stage a `pending` config, which the next start uses and reverts to `stable` five minutes later unless `http/config/promote` confirms it. With Home Assistant stopped, `stable` can be edited directly.
- With `use_x_forwarded_for`, a request whose peer is not in `trusted_proxies` gets a 400, and Home Assistant logs "Received X-Forwarded-For header from an untrusted proxy". The list now names ingress's GUA, ULA and reserved IPv4, in place of the `127.0.0.1/32` cloudflared used. ingress has no temporary addresses, so over IPv6 it connects from its EUI-64 GUA.
- After a restart of the stack, Home Assistant answered `/manifest.json` five seconds after its start, then no request at all until `/api/` answered about seven minutes in; ingress's Caddy gives a 504 meanwhile.
