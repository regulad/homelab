# authentik is configured by tofu/authentik, signed in with a token a blueprint defines (2026-11-22)

- **No `ak` command makes an API token** in 2026.8.6: `create_recovery_key` makes a one-time login link, and `AUTHENTIK_BOOTSTRAP_TOKEN` only feeds `blueprints/system/bootstrap.yaml`'s `state: created` token for `akadmin`. A blueprint of our own sets a token's `key` directly, as the bootstrap one does, and with the default `state: present` a changed key overwrites the token's.
- **The worker applies blueprints as the image's `authentik` user,** uid and gid 1000: `lifecycle/ak` chowns as root, then drops to it with `setpriv`. A blueprint holding a secret is `0640`, group 1000. Its file watcher passes only created and modified events, and discovery applies a blueprint only when the file's sha512 differs from the one it last applied, so a secret behind `!Env` or `!File` would not re-apply when it changed; the key is written into the file instead. The stack's restart applied the new blueprint in the worker's startup discovery, within seconds of its start.
- **The provider requires its `token` even to validate,** so `AUTHENTIK_TOKEN` in the environment breaks `tofu validate` without secrets; the token is the input `authentik_token`, exported as `TF_VAR_authentik_token`.
- **Provider 2026.8.2 against authentik 2026.8.6, at import:**
  - authentik returns `redirect_uri_type = "authorization"` on each OAuth2 redirect URI; a config that omits it plans a change.
  - The provider's default `flags` turn `core_default_app_access` off, while authentik's own default (`AppAccessWithoutBindings`, in `authentik/core/apps.py`) is on; the tenant stores neither, only the system flag `setup`.
  - authentik keeps every system flag, such as `setup`, on any settings write and returns none of them.
  - A certificate-only key pair's empty private key reads back as `"\n"`. Sent back, DRF's default trimming makes it `""` again.
  - The LDAP source's `bind_password` is never read back, so every update sends it.
  - The order of `property_mappings` read at import was not the data sources' order. The first apply sent the same set again, and later reads keep the configuration's order.
  - The LDAP source's peer and client certificates, and the settings' `base_url` and `impersonation_require_reason`, are not in the provider; its updates leave them as they are.
- **Saving an LDAP source starts its sync and connectivity check at once:** its schedule specs set `send_on_save`. The adoption's update of `freeipa` ran a full sync, which finished without errors.
- **A run cut short by an unreachable host keeps AIDE's hold on it:** the first `host_files` apply marked the run's start on authentik, then failed to authenticate for the next task, so no refresh play released the hold until the next run's end.
- **alock's hook refuses a git command it cannot parse that mentions alock,** as one that might change its `alock.*` git settings: a `git commit` whose heredoc message named `.alock.json` was refused, while one without the name passed. `git commit -F <file>` passes.
