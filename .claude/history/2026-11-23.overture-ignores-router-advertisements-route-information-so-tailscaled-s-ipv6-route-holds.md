# overture ignores router advertisements' route information, so tailscaled's IPv6 route holds (2026-11-23)

- overture's tailnet IPv6 address answered nothing from any peer while its IPv4 address did. Its route to `fd7a:115c:a1e0::/48` pointed out en5 to tailscalerouter's link-local (`fe80::be24:11ff:fe53:2c15`), learned from the Route Information Option that tailscalerouter's radvd advertises to the LAN. tailscaled's own `/48` through `utun0` was missing. Packets arrived through `utun0`, but replies left by the LAN and were lost.
- How it showed: ping and SSH to the IPv6 address timed out, and a closed port timed out instead of refusing. tailscaled's PeerAPI port did answer over IPv6, because its netstack serves PeerAPI without the kernel. IPv4 was unaffected: tailscaled's `100.64/11` and `100.96/11` through `utun0` are narrower than DHCP option 121's `100.64/10`, so they win. The ULA range has the same `/48` on both sides, so the two routes collide.
- macOS keeps one unscoped route per prefix. Whichever `/48` comes first holds the slot. tailscaled's BSD router logs a failure only on a non-zero exit, and macOS's `route` always exits 0 (network_cmds `route.c`: `newroute(argc, argv); exit(0);`). So tailscaled's failed add was silent, and the router recorded the route as installed and never retried. `/opt/homebrew/var/log/tailscaled.log` had no `addr add failed` line.
- `net.inet6.icmp6.nd6_process_rti` (XNU `nd6.c`, default 1) gates the parsing of Route Information Options. It is present on macOS 27.0.1. arawi's advertisements carry no route information, so at 0 overture loses only tailscalerouter's two routes, and reaches the OCI pubsub `/64` through arawi's static route instead.
- Reports say `/etc/sysctl.conf` has been ignored for network keys since Monterey, and overture has none. So the `tailscale` role sets the sysctl from a launchd job at every boot, `xyz.regulad.homelab.ignore-route-info`, following the `xyz.regulad.<project>.<name>` labels of aaoracled and blackb0x.
- A learned route is not to be removed with `route delete`. The kernel's route-information entry stays marked installed, and when it expires `defrouter_delreq` deletes by prefix and mask: XNU's `RTM_DELETE` never checks the gateway. That would remove whatever `/48` is there by then. `ndp -R` (`SIOCSRTRFLUSH_IN6`) purges the route-information entries with the default routers, on every interface; the default routers return with their next advertisement.
- After 2026-11-22's switch to `-F /dev/null`, Ansible's become on overture failed with "Missing sudo password". dotfiles' pam_rssh signs overture's sudo with the forwarded agent, and the forwarding had come from the operator's `~/.ssh/config` (`ForwardAgent yes` for the Macs). Each stage now forwards the agent to the `macos` group too, as it does for the hosts that set `pam_rssh_enabled`. Within Ansible's default timeout (12 s in its error), the become fails "waiting for privilege escalation prompt" unless Bitwarden's approval comes first.
- On its first load on 2026-11-23, the job found the learned `/48`, flushed the routers and restarted tailscaled. The `/48` then went through `utun0`, the IPv6 default routes came back through arawi on en5 and en0, and the tailnet IPv6 address answered ping and SSH from WINLITE. Ansible's tailnet connection survived the restart: the run that loaded the job finished normally.
- tailscaled's launchd job is `system/sh.brew.tailscale`. On 2026-11-23 Homebrew's `tailscale` command was 1.104.2 while the running `tailscaled` was still 1.102.5.
