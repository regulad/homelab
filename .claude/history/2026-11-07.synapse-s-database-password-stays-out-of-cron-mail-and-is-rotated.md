# Synapse's database password stays out of cron mail, and is rotated (2026-11-07)

- The state compressor's cron line passed Synapse's database URL, password included, to `synapse_auto_compressor -p`. Cron puts the command in the subject of each mail it sends for a job and in its log of the command. The line piped only stdout to `systemd-cat`, while the compressor logs through `env_logger`, to stderr, so every run became cron mail.
- `synapse_auto_compressor` 0.1.4 takes its database only through `-p`, with no environment variable or file, and prints the URL when it cannot connect: it panics with "Error occured while connecting to {db_url}", and its manager reports "Failed to connect to {db_url}". So the fix takes the password out of the connection itself: matrix's PostgreSQL 18 keeps Ubuntu's `local all all peer`, and the job runs as `synapse_user`, a system user named for the database role, connecting with `host=/var/run/postgresql user=synapse_user dbname=synapse`. `2>&1` sends its log to the journal as `synapse_auto_compressor`, and cron mails nothing for it.
- `homeserver.yaml`, which renders `synapse_secrets`, had no `secret: true`, so a run with `--diff` would have printed its passwords; it has it now. Removing a task's `no_log` exposes the old content in the next `--diff`, as the check run before this apply showed with the old cron line.
- The rotation set the new password with `ALTER ROLE` first, piped from SOPS into `psql`'s stdin on matrix, then re-rendered `homeserver.yaml` and restarted Synapse: its pooled connections kept working in between. Synapse's only other consumer of the password was the compressor; the bridges keep their own SQLite databases.
- `psql` against the `postgres` database warns of a collation version mismatch: created with glibc's 2.36, while the system provides 2.43.
- Synapse logs "Metric named cache_lru_cache_… already registered for server" at ERROR level at every start; the 2026-11-06 log has 27 of them.
