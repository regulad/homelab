# peppercord and cordpepperer: on the tailnet, with webhookd behind Tailscale Serve (2026-11-16)

- regulad/tailscale-acls has `tag:ci-client-peppercord`, for PepperCord's GitHub Actions runners, and `tag:ci-server-peppercord`, for the two hosts. Its one grant lets the client reach tcp:8108 on the server; the server tag has no grant of its own, only what every node gets. They were first added (`ac40112`) as `ci-client--peppercord` and `ci-server--peppercord`, but `--` stands for `.` in that policy's names. The rename kept the old tags beside the new ones while the joined nodes moved (`07ed548`), as the tailscale role fails on a node whose tags differ from its declared ones rather than re-tag it. `POST /api/v2/device/<nodeId>/tags` re-tagged each node in place, with no re-authentication.
- The `internet-only` security group sees a guest's Tailscale traffic only encapsulated, so on these hosts the tailnet's policy is what keeps the bots off internal addresses over Tailscale. `accept_routes: false` is load-bearing there: with the subnet routes, the bots would reach what the tailnet opens to every node, such as ingress's web, through the edge routers.
- Adding `device_passthrough` for `/dev/net/tun` to a running container is an in-place update that the bpg provider follows with a reboot of the container (`rebootRequired` in its container update): about 26 s each here, and both bots answered `/health` again afterwards.
- On a host without Tailscale, `--check --tags tailscale` stops at "Install Tailscale" with "No package matching 'tailscale' is available": check mode never writes the apt source. pkgs.tailscale.com publishes Ubuntu 26.04 (`resolute`), with the same key hash as the other releases.
- The role's `tailscale_api_token` had stopped working: minting the join key failed behind `no_log`, and `GET https://api.tailscale.com/api/v2/tailnet/-/keys` with it answered `401 {"message":"API token invalid"}`. That GET, which returns only key metadata, is a read-only way to test the token. Parker issued a new one on 2026-11-16; it expires 2027-02-14T05:18:46Z.
- azlux's repository publishes Debian suites alone (bookworm, bullseye, buster, trixie, sid and the stable aliases), so these Ubuntu hosts take webhookd from upstream's release archive. GitHub's release API gives each asset's SHA-256 (`digest`); the arm64 one matches the checksum mail pins.
- Serve's listener binds each tailnet address on `tailscale0` (`100.87.x.x%tailscale0:8108`), so webhookd on `127.0.0.1:8108` shares the port without conflict, and neither is reachable from the hosts' Podman bridges. Through Serve, webhookd's `http` log names the caller's own tailnet address.
- webhookd 1.22.1: without a `.htpasswd` in its working directory it asks for no basic auth; in `buffered` mode (`WHD_HOOK_DEFAULT_MODE`) the hook's exit status sets the response's, 0 to 200 and 1 to 99 to 500; it passes a request's query parameters and headers to the hook as environment variables, so a hook names its commands by path.
- The `aide_written` callback recorded nothing for `unarchive`, so files `host_files_archives` extracted, such as mail's `/usr/local/bin/webhookd`, never reached AIDE's baseline. It now records each member an `unarchive`'s `include` names, under its `dest`.
- The first pipeline deploy, PepperCord run 43814359689 at 06:06:58 UTC on 2026-11-16, joined as `tag:ci-client-peppercord` through a GitHub OIDC federated credential and reached both hooks over IPv6 (`fd7a:115c:a1e0::8c38` in webhookd's log). Each host pulled the new image within 2 s and restarted its stack, and both bots were up on the new release 30 s after the calls.
