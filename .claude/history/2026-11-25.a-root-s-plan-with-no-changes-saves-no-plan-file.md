# A root's plan with no changes saves no plan file

- `tofu plan -out=<file>` writes the plan file whether or not the plan has changes: each commit had left a 113 KB `cloudflare@<commit>.tfplan` with none. Its refresh stays in memory, so no state version is written; the s3 backend's `use_lockfile` lock object exists only for the plan's duration.
- A root's plan listed its commit-named plan file in `generates`, so each new commit renamed a file every plan had to produce, and every one of the 19 OpenTofu steps planned again at each commit, about 7 minutes of a pass. The plan now deletes the file when `tofu plan` exits 0, and keeps one only while the step's changes wait in `.task/pending/<step>`: a `status:` check plans again when that file is missing for HEAD's commit.
- What decides whether a step runs, and who decides it:

  | Question | Who answers it | How |
  |---|---|---|
  | Which files and signals are a step's inputs? | homelab | `sources:` lists, `tasks/upstream.sh` |
  | What are the current values of the non-file inputs? | homelab | digests written to `.task/upstream/<step>` |
  | Have these exact inputs already been processed successfully? | go-task | it hashes `sources` and compares with `.task/checksum/<task>` |
  | Does live infrastructure match what's declared? | neither: OpenTofu and Ansible | only a real `tofu plan` or `--check` |

  go-task records inputs, never outputs or live state, so a skipped step means only that nothing fed into it has changed since it last ran cleanly; drift made outside the pipeline shows only under `--force`.
