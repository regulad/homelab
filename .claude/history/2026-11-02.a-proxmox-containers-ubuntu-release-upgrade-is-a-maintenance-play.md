# A Proxmox container's Ubuntu release upgrade is a maintenance play (2026-11-02)

- **It works.** `do-release-upgrade` took an unprivileged container from Ubuntu 24.04 to 26.04.1 LTS unattended in about ten minutes, on PVE 9.2 with pve-container 6.1.15 and kernel 7.0.14. A throwaway container (CT 212, from the 24.04 template, with ingress's settings and a Podman 4.9 Quadlet) was upgraded by hand, then by the play.
  - Neither vendor documents it as a tested path. Proxmox staff say to upgrade a container from inside, with its own tools, as on a VM, after a backup. The upgrader has no container-specific path: its kernel check only logs, and its 26.04 GRUB quirk notes that containers have no GRUB. Its one hard gate, cgroup v1, does not apply: PVE 9 runs cgroup v2 alone.
  - pve-container refuses an Ubuntu version it does not know when it starts a container (`$known_versions` in `PVE/LXC/Setup/Ubuntu.pm`), and starts a newer unknown one with a warning. 6.1.15 knows 26.04.
  - 26.04.1 was offered to 24.04 without `-d` by 2026-11-02.
- **The non-interactive frontend** (`--frontend=DistUpgradeViewNonInteractive`) replies "n" at each conffile prompt, keeping the old file, answers yes to its own questions, and does not reboot (`RealReboot` is false). It kills a script that is silent for 2400 s. It left `/etc/cron.d/e2scrub_all.dpkg-dist` and `/etc/ca-certificates.conf.dpkg-old`. Its log's `failed to import AptClone` is harmless.
- **A container upgraded from the 24.04 template booted degraded.** 26.04's `netplan-configure.service` ends with `udevadm control --reload` and `udevadm trigger`, which fail where there is no udev. Proxmox's 26.04 template clears both with `/usr/lib/systemd/system/netplan-configure.service.d/override.conf` ("PVE: avoid udev trigger in container"), which no package owns and pve-container does not write. The `lxc_guest` role now writes the same drop-in to `/etc`.
- **Podman 4.9 to 5.7** keeps the database's empty driver record, and 5.7's `checkRuntimeConfig` compares it as strictly as 4.9's. With `/etc/containers/storage.conf` (no driver, the roots named) Podman 5.7 ran, the Quadlet came back, and `podman system check` passed.
- **In the play:**
  - Ansible discovered `/bin/python3.12`, which the upgrade removes at its end, so the next module failed. The play pins `/usr/bin/python3`, which points at the new release's Python afterwards, and waits on the upgrade with `raw`.
  - `raw` through `proxmox_pct_remote` runs on a terminal: its output comes wrapped in carriage returns and escape sequences (`\rloaded\e[m\r\n`), so values are matched within it, not compared whole.
  - The reboot module compares the kernel's boot ID by default, which a container never changes; `boot_time_command: systemctl show --property=UserspaceTimestampMonotonic --value` does.
  - A task delegated to the container's node, with `ansible_connection: ssh` and `ansible_user: root` in its own vars, runs `pct snapshot` there.
  - Regex escapes in Ansible: in a conditional (`when`, `until`, an assert's `that`) written as a plain scalar, `'\\b'` matches a word boundary; in a templated string such as `msg`, `'\\w'` matches nothing and `'\w'` works.
- **On 26.04 in a container**, `/bin/pasta --version` segfaults, and Podman warns of it; rootful Podman does not use pasta.
