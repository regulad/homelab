# nexus encrypts its secrets and API keys with keys of its own (2026-11-09)

- Nexus's health check "Default Secret Encryption Key" fails until a secrets file names an active key. Both defaults it replaces are in Nexus's public source, the same in every installation: the secrets table's default key is the password `changeme` (`nexus.mybatis.cipher.password`'s default, `SecretsServiceImpl`), and the fixed encryption is password `changeme`, salt `changeme` and IV `0123456789ABCDEF` (`MyBatisCipher`), with AES/CBC/PKCS5Padding over PBKDF2WithHmacSHA1. The secrets table held svc-nexus's LDAP bind password and the `regulad` logins of the `docker-io` and `ghcr-io` proxies.
- On 3.97 an API key's secret is in the secrets table (`api_key_v2.secret`, through `SecretsService`); the fixed encryption covers only `api_key_v2.principals`, whose username is also stored in plaintext beside it. The 3.97 upgrade's `ApiKeyToSecretsTask` copied the old `api_key` table's rows to `api_key_v2` without deleting them, so tokens from before it stay there under the fixed default, which no task re-encrypts; resetting those tokens is what retires them.
- `NEXUS_SECRETS_KEY_FILE` becomes `nexus.secrets.file` at bootstrap (`NexusPropertiesVerifier`). Nexus reads `active` and `fixedEncryption` once, at start: new secrets get the active key at once, and older ones, whose `key_id` is NULL, still decrypt with the default until re-encrypted. The fixed encryption applies at once too, so API keys fail to authenticate from that restart until the principals' re-encryption.
- "Re-encryption required" counts secrets whose `key_id` differs from the active key or is NULL, and reports healthy with "Re-encryption in progress" while its task runs. Both re-encryption tasks are hidden from `/v1/tasks` (`nexus.secrets.re-encrypt.task.visible` and `nexus.reencrypt.principals.visible` default to false); the principals' task reports its counts only in `nexus.log`.
- The principals' task decrypts every row with `previousFixedEncryption`, or the defaults, and cannot tell rows it has already moved; under CBC a wrong key passes the padding check about once in 256 and would overwrite that row with garbage. `nexus-reencrypt` therefore runs it only while `/mnt/nexus/data/etc/fixed-encryption.sha256`, on the data volume with the database, names another fixed encryption.
- The run: the secrets' task finished in seconds; the principals' re-encrypted 7 rows with 0 failures in 14 ms. The first rollout restarted Nexus twice, once from `host_files` for the new file and once from the `quadlet` handler for the new mount.
- The key file sits on the container's root disk, which the weekly vzdump to CephFS backs up with the data volume; prodingus's restic `cephfs` job copies `dump/` to B2, which every host's B2 key can read, and immich, timemachine and tvheadend mount all of CephFS, `dump/` included. The custom key therefore guards only copies of the database taken without that root disk, and the backups made before today hold the three logins under the default key.
- `sops exec-env` refuses `nexus_servers.sops.yml` now that it holds a map (`nexus_secrets_keys`): "cannot use complex value in environment". `sops -d --extract '["nexus_api_password"]'` reads a single value; Ansible's SOPS vars plugin reads the file as before.
- Unrelated, found while checking: the `docker-io` proxy's remote is `https://docker.io` with index type `REGISTRY`, and docker.io answers every `/v2/` path with a 302 to `www.docker.com`, so each manifest comes back 400 "Invalid manifest", every image resolving to the same digest. None of the 133 days of request logs holds a `docker-io` manifest request.
