# MTA-STS enforces, TLS-RPT reports to postmaster, and DANE pins mail's key (2026-11-05)

- regulad.xyz, nefumllc.com and regulad.net serve their MTA-STS policy with `mode: enforce`, and publish `_smtp._tls` records sending senders' daily TLS reports (RFC 8460) to `postmaster@regulad.xyz`. That address resolved nowhere, so mail to it was refused; it is now one of the owner's `mail` values in FreeIPA, which the alias map delivers to `regulad@regulad.xyz`. svc-ansible may only read, search and compare another user's `mail` (`rsc`), so the change was made as admin, through the JSON-RPC API's `user_mod` with `addattr`.
- A TLSA record, `_25._tcp.mail.regulad.xyz 3 1 1`, pins the SHA-256 of mail's certificate's public key, an ECDSA P-256 key. `3` (DANE-EE) checks neither the certificate's issuer nor its name, as RFC 7672 recommends for SMTP; `1` (SubjectPublicKeyInfo) matches the key alone, so the record survives renewals that keep it. regulad.xyz is DNSSEC-signed, and senders that use DANE require the match for each recipient domain whose MX lookup they can validate: nefumllc.com and regulad.net once their DS records publish.
- certbot made a new key at each renewal, which would have left the record stale at the next one. The `certbot` role's per-certificate `reuse_key` sets `reuse_key = True` in the renewal file, and `--reuse-key` at issue; elsewhere it leaves the option out. To change mail's key, publish the new key's TLSA beside the old one, wait out the TTL, switch keys, then remove the old record.
- `openssl s_client -starttls smtp -dane_tlsa_domain mail.regulad.xyz -dane_tlsa_rrdata "3 1 1 <hash>"` checks the server against a record: it reported the record matched the end-entity certificate. From OCI instances, port 25 to mail's public IPv4 address does not answer; tests of it go from outside OCI.
- A plan made and applied in one command was refused by Claude Code's permission check as a blind apply; making the saved plan, reading it, then applying it in a second command passed.
