# Doppelganger's sign-in with Google moves to new OAuth clients, whose files SOPS keeps (2026-11-19)

- The restored project `pure-toolbox-429813-a4` kept answering `Error 401: deleted_client` for its old client three days after the restore, past the 1 to 3 days Google's documentation allows, and Google's support needs a paid plan. New web clients made in the same restored project worked at once: `doppelganger`, for doppelgangerhq.com, and `doppelganger-test`, whose origins are `http://localhost` and `http://localhost:3000`.
- Accounts survive a change of client. Google's `sub` belongs to the Google account, the same under every client, and Supabase keys each Google identity by `provider_id`, which is that `sub`; nothing in an identity records the client.
- Doppelganger signs in through Google Identity Services, One Tap and the button in popup mode, and Supabase's `signInWithIdToken`, which checks the ID token's audience against the project's Google client IDs. The redirect URI and the client secret serve only Supabase's own redirect sign-in, which Doppelganger does not use. Local development signs in to the production Supabase project.
- `tofu/gcp/oauth-clients.sops.json` keeps the file the console downloads for each client, `{"web": {…}}`, by project, then slug. Its `.sops.yaml` rule, `encrypted_regex: ^client_secret$`, leaves every other value plaintext, so `jsondecode(file(…))` reads the IDs without decrypting; the MAC still covers every value. `sops encrypt --filename-override <path> /dev/stdin` encrypts from a pipe under that path's rule, so the plaintext never touches disk.
- The Supabase Management API returns each secret in a project's auth config as hex HMAC-SHA256 of the secret, keyed by the project ref, as the Supabase CLI's `sha256Hmac(projectRef, plaintext)` computes it; comparing that digest shows whether a secret is set, without reading it. Provider 1.11.1 keeps declared secrets from state, so a declared secret shows no diff, and a change made in the Dashboard shows in no plan. A sensitive value inside `auth`'s `jsonencode` makes the whole attribute sensitive: review its diff in `tofu show -json` with the secret taken out.
- The API folds `external_google_additional_client_ids` into `external_google_client_id`, as one comma-separated list, and reads the former back as null. Declaring it made the provider fail the apply after the update had been made ("inconsistent values for sensitive attribute"), and state kept the provider's result. Declare the one list instead, web client first: the redirect sign-in uses the first ID with the secret.
- Next.js writes `NEXT_PUBLIC_` values into the bundles at build, so the browser gets the client ID from the image's `.env.local.public`; the copy `web.env` passes at runtime reaches only server code that reads it when the process starts.
- An `ansible-generated` run can take one inventory source, `-i inventory/oracle.terraform_state.yml`, when another root's state, such as `tofu/gonkputer`'s, isn't prepared; the `group_vars` and `host_vars` beside it still load.
