# doppelgangerhq.com boots the newest generic 6.8 kernel (2026-11-01)

- Redroid's only kernel dependency is `binder_linux`, which Ubuntu 24.04's generic 6.8 kernels ship in `linux-modules-extra-<version>-generic`; `linux-image-generic` depends on that package, so every new generic kernel brings it. No installed kernel has `ashmem_linux`, and none is needed: the devices run with `androidboot.use_memfd=true`. `/etc/rc.local` loaded binder with `devices=binder,hwbinder,vndbinder`, and that parameter matters: Ubuntu builds binderfs as a module with `CONFIG_ANDROID_BINDER_DEVICES=""`. The host gets no binder device nodes, and the parameter names the devices every binderfs mount starts with, one mount per Redroid container. Nothing ordered rc-local before docker.service; it simply finished first. The host_vars now load binder from modules-load.d, with its options in modprobe.d. systemd-modules-load runs before `sysinit.target`, so binder is loaded before Docker starts.
- From 2025-11-01 the host booted only 6.8.0-87. `/etc/default/grub` set `GRUB_DEFAULT=saved` and `GRUB_SAVEDEFAULT=true`, and that day's `grub-set-default` chose 87's entry, so every later kernel was installed and never booted. 87 left noble-updates and noble-security on 2026-06-14/15 while still running, so apt could no longer reinstall it. Its image, modules and modules-extra debs are still on the Launchpad librarian (IDs 824259645, 823874005, 823874006), and copies are in the operator's `docs/snapshot/doppelgangerhq.com/debs-6.8.0-87/`.
- `/etc/default/grub` is back to Ubuntu's `GRUB_DEFAULT=0`, and the Oracle flavour (`linux-oracle`, then at 7.0.0-1013) is purged. Ubuntu 24.04's GRUB has no flavour preference: it lists kernels by version, and `GRUB_TOP_LEVEL` names one exact kernel file. With both flavours installed, the Oracle HWE kernel came first. Now the first entry is always the newest generic 6.8 kernel, which unattended-upgrades installs and then boots through `Automatic-Reboot`, right after the run. Its 2.9.1 reboots after any daily run that finds `/var/run/reboot-required`, even one that upgraded nothing, so a kernel installed by Ansible or by hand also gets booted at the next run.
- 6.8.0-147's configuration matches 87's in every option Redroid uses. On it, a Redroid 12 device reached `sys.boot_completed` in about 15 s, with 205 binder services. The kernel's `binder_linux: … cannot find target node` / `transaction async to 0:0 failed … -22` lines are routine: 87 logged 29 in its last boot.
- Starting any Redroid container rewrites host-wide sysctls until the next boot. `kernel.modprobe` becomes empty, which stops all on-demand module loading, so any module the host needs later must load at boot, as firewalld's nft modules do from modules-load.d. It also sets `kernel.pid_max` 65535, `kernel.panic_on_oops` 1, `kernel.kptr_restrict` 2, `kernel.sysrq` 0, `kernel.perf_event_paranoid` -1 and `vm.overcommit_memory` 1.
- The app's `cron` container calls `/api/cron` every minute. That endpoint runs `compose down -v` on every running device whose owner has no active Pro or Plus subscription and whose `lastConnectedAt` is more than five minutes old. A websocket connect brings a stopped device up, but the scrcpy route only writes `lastConnectedAt` after its scrcpy-server retries finish, which takes longer than Android's ~15 s boot. Without an active subscription, a device starting with a stale `lastConnectedAt` is torn down at the next minute tick, and a reconnect during that teardown can leave the scrcpy container running without the Redroid one. Stopping `doppelganger-cron-1` for the length of a test sidesteps this. A device brought up outside the app also never gets a fresh `lastConnectedAt`, so the next tick reaps it.
- Android 12's `com.android.pacprocessor` crashes at each device boot with `WebView cannot be used with device protected storage`. The device's proxy.pac is therefore never evaluated: `PacProxySelector` returns `NO_PROXY`, and the device connects directly.
- This was the host's first boot with firewalld, installed 2026-10-30. systemd broke an ordering cycle by dropping `cloud-init.service`, cloud-init's network stage. The cycle runs from cloud-init.service, ordered before `sysinit.target`, through systemd-networkd-wait-online, systemd-networkd and `network-pre.target` to firewalld.service. That unit is ordered `Before=network-pre.target`, yet keeps default dependencies, so it waits for `basic.target` and therefore `sysinit.target`. cloud-config and cloud-final still ran, and networking came up.
