# authentik's Podman volumes, its database, on a 4 GB disk of their own (2026-11-22)

- **Before the move, every piece of authentik's state was on CT 201's 16 GB root disk:** its database, `/data` and `/templates` are Podman's named volumes, about 254 MB together, nearly all PostgreSQL. The disk is now `mp0`, `rbd:vm-201-disk-1`, at `/var/lib/containers/storage/volumes` with `backup = true`. The stack's `.env`, compose file and blueprint in `/opt/authentik` stay on the root disk, as host files Ansible renders.
- **peppercord's procedure moved it unchanged.** The unit was disabled and stopped, and `podman-compose down` removed the containers. The volumes directory was renamed aside, with an empty `0700` directory left for the mount. bpg/proxmox 0.122.0 added the mount point in place in 20 s and rebooted the container. The new ext4's `0755` root was set back to Podman's `0700`, then `cp -a` and `diff -rq` brought the volumes back; the only difference was the new disk's `lost+found`. Ten tables' row counts matched before and after, and the API answered with the `homelab-tofu` token 35 s after the stack started.
- **No watchdog reboots authentik:** prodingus's webhookd hooks reboot only freeipa (a VM that no longer exists), cordpepperer, peppercord and ncsusplitt, so nothing cut the move short, unlike peppercord's.
- **PostgreSQL's data directory belongs to uid 70,** the Alpine image's `postgres`, which the container has no name for, so `stat` shows `UNKNOWN`; `cp -a` keeps the uid.
- **Ad hoc SSH to prodingus by its full hostname now fails** for the operator's own `ssh`: since Ansible stopped reading `~/.ssh/config`, `prodingus.tail11540.ts.net` alone logs in as the local user, `regulad`, and is refused. The SSH configuration's `prodingus` alias, which logs in as root, still works.
