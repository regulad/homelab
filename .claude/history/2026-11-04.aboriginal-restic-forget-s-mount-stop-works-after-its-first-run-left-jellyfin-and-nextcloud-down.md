# aboriginal: restic-forget's mount stop works, after its first run left Jellyfin and Nextcloud down (2026-11-04)

- **The first run of the forget job's mount stop** (2026-10-31), from the timer at 17:52, failed in `ExecStartPre` on `comm: file 1 is not in sorted order`. Services run under the host's `LANG=en_US.UTF-8`, and there `comm` rejected the order `sort` gave it: `comm --check-order` over the live unit list exits 1 in that locale and 0 in C. No forget or prune ran. The pre-step's shell now exports `LC_ALL=C`.
- **The stop left `/mnt/nas` bound to a dead mount.** Its unmount failed, "target is busy": `mnt-media.mount`'s fuse-overlayfs, which systemd logged as "remains running after unit stopped", still held its lower directory `/mnt/nas/media` open. It lived on because regulad's rootless bandcampsync bound `/mnt/media/Bandcamp` privately (`rprivate`, Podman's default), which kept the overlay's FUSE connection alive in its own mount namespace after the host's unmount. The stop of `mnt-restic.service` then killed the restic serving `/mnt/nas`. Every remount failed with "Transport endpoint is not connected", and both stacks and smbd stayed down.
- **Finding a FUSE mount's holder:** `/sys/fs/fuse/connections/<n>` lists each live connection. One with no mount in the host's `/proc/self/mountinfo` is held elsewhere, and `grep -E '^[0-9]+ [0-9]+ 0:<n> '` across `/proc/*/mountinfo` finds the process whose namespace has it. `/proc/<pid>/fdinfo/<fd>` of a daemon's `/dev/fuse` names its `fuse_connection`.
- **The restart list named vanished units:** the comparison also caught the mounts of the containers that stopped with the stacks (their netns, overlay, shm and volume mounts), which `systemctl start` then found "not found". `ExecStopPost` now starts only the units whose `LoadState` is `loaded`.
- **bandcampsync binds all of `/mnt` as a slave** (`Volume=/mnt:/mnt:rslave`, with `DIRECTORY=/mnt/media/Bandcamp`), so the host's mounts and unmounts beneath `/mnt` reach it: the container's mountinfo shows `master:<n>` for the host's `shared:<n>`. A bind of `/mnt/media/Bandcamp` itself is a mount of the overlay, which the host's unmount of `/mnt/media` does not detach whatever its propagation. The image's entrypoint only sets its user's IDs and chowns nothing, so the wider bind changed no ownership. The quadlet is regulad's own, edited by hand, not managed here.
- **`mnt-nas.mount` unmounts lazily** (`LazyUnmount=yes`): it is a read-only bind, so detaching it while held loses nothing. The overlays keep ordinary unmounts: an overlay still held elsewhere, detached lazily, would leave its fuse-overlayfs on the same upper and work directories as its remount. systemd's mount units cannot wait and retry an unmount: they take no `Exec*` commands, `TimeoutSec=` bounds only the `umount` command, and a failed unmount is not tried again.
- **The recovery:** stop bandcampsync, after which the old fuse-overlayfs exited and its connection closed; stop `mnt-nas.mount`; start the overlays, the Nextcloud remap, smbd and both stacks, which pull in `/mnt/nas` from the running restic mount; then start bandcampsync on its new bind.
- **The run skipped by the failure, started by hand at 18:45,** forgot and pruned in 4 minutes. The overlays and `/mnt/nas` unmounted with nothing busy and remounted after it, and bandcampsync's `/mnt/media` moved to the new overlay without a restart. Jellyfin's first healthcheck, a second after its container starts, fails and leaves its transient unit failed until the next check passes.
- **A stale decrypted passphrase:** the main checkout's `tofu/backblaze/secrets.auto.tfvars.json` still held the state passphrase from before its rotation (3e866e4), so the restic role's `tf_output` lookup failed with `cipher: message authentication failed`. `prepare.sh` refuses to overwrite a decrypted file that differs from SOPS. Once the copy matches the SOPS file from before the rotation (`git show 3e866e4^:tofu/backblaze/secrets.sops.json | sops decrypt --input-type json --output-type json /dev/stdin`), it holds no local edits, and decrypting the current file over it is safe.
