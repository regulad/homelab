# doppelgangerhq.com prunes dangling Docker images by a timer, not root's crontab (2026-11-04)

- Root's crontab held only `0 4 * * * docker image prune -f` beside its `PATH` line. `docker-image-prune.timer` and its service, from `host_files`, now run the prune, and the crontab is deleted.
- Before systemd 258, a timer cannot have both a fixed and a per-run random delay. `FixedRandomDelay=yes` turns `RandomizedDelaySec=` itself into a fixed delay. `RandomizedOffsetSec=`, the fixed offset that combines with `RandomizedDelaySec=`, arrived in systemd 258, and Ubuntu 24.04 has 255. The timer draws a new delay within the hour after 04:00 for each run.
- `Requisite=docker.service` starts the prune only while Docker is active, so the timer never starts Docker and with it the devices. When Docker isn't active, the prune's start fails at once, as `systemd.unit(5)` documents for `Requisite=`. The cron line likewise ran nothing then, because `docker` could not reach its daemon.
- Podman hosts already prune dangling images: `podman-auto-update.service` runs `podman image prune -f` after each auto-update. On 2026-11-04, aboriginal had none dangling and all 8 of its images in use. aboriginal's own hourly Docker prune jobs had gone with Docker in its cleanup.
