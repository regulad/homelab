# lime reports to Sentry from its release builds

- `tofu/sentry`'s `lime` project (platform `rust`) takes lime's reports. Only lime's own releases send any: the `sentry` Cargo feature is off by default, and the DSN is compiled in only with it and `LIME_RELEASE`, which its release workflow sets. A build from source, a distribution's included, has none of Sentry's crates. That fits what Debian and Fedora expect of telemetry: opt-in, or absent from their own builds. `DO_NOT_TRACK` turns it off; empty, `0` and `false` count as unset, as Warlock reads it.
- A run is a start of the daemon, one release-health session, started by hand once the scope holds that start's random ID, so that the session carries it. Each password sent at the pre-boot unlock is an `unlock` transaction tagged `unlocked` or `refused`. lime checks a booted Mac every 30 seconds, so those checks aren't counted, or a Mac would make thousands of transactions a day.
- Sentry's Rust SDK on Linux uses reqwest with native-tls, which links the system's OpenSSL 3 (`libssl.so.3`) and uses its CA store, so the binaries need `libssl3`. Its `ureq` and rustls transports bundle Mozilla's roots, `webpki-root-certs`, under CDLA-Permissive-2.0, which lime's `about.toml` doesn't accept. On Linux, `sentry-contexts` sends the kernel's `uname` fields, the architecture and the Rust version, and sets `server_name` to the hostname unless the app sets one; lime sets `lime`. Sessions need the SDK's `release-health` feature, which `default-features = false` turns off.
- lime's releases come from an annotated `v<date>` tag. The tag's message is the release notes. A second release that day is `_1` in the tag and `+1` in Cargo.toml, as Koala's are. Each architecture's archive comes with a `.sha256`. `THIRD-PARTY-NOTICES.txt` is written by cargo-about 0.9.3, pinned by its tarballs' SHA-256, from `about.toml` and a plain-text `about.hbs`. Handlebars escapes HTML in `{{…}}`, so the template uses `{{{…}}}`.
- A `dist` Cargo profile keeps line tables for the release build. The workflow publishes a stripped copy and uploads the unstripped one, matched by its ELF build ID, which Sentry shows as a debug ID with the first three groups byte-swapped (`d63851aa-fed2-c53a-…` is `aa5138d6-d2fe-3ac5-…`).
- tofu/github's `prepare.sh` refuses to rewrite `secrets.auto.tfvars.json` when it differs from a fresh decryption, as it does once a new token is added to a SOPS file it reads. When a comparison by key path shows that only the new key differs, deleting the gitignored file lets `prepare.sh` write it again.
