# clamonacc: a clamd of its own on doppelgangerhq.com, dodo on the shared one, and clamonacc's own bugs (2026-10-30)

- `clamonacc_clamd_local` runs the packages' clamd and freshclam on a host outside the homelab, so its files stay on it: clamonacc reaches clamd at `/run/clamav/clamd.ctl` with `--fdpass`, so clamd, running as `clamav`, scans files only root can read, and skips the `clamav` user's own files. Debian's and Ubuntu's `clamav-daemon` units carry `ConditionPathExistsGlob` on `main` and `daily`, so clamd starts only after freshclam's first download, which on doppelgangerhq.com came within ten seconds. clamd holds about 980 MiB there, as the shared clamd does.
- clamonacc gives up on a watched tree if a directory in it vanishes while it walks the tree at start ([#186](https://github.com/Cisco-Talos/clamav/issues/186), open since 2021): it logs `could not watch path '/home', No such file or directory` and runs on, active to systemd, with `/home` unwatched until it restarts. On dodo, Ansible's temporary directory under `/home/regulad` vanished during the role's first start; the handler's restart three seconds later watched every tree. `clamonacc-mail` now mails those lines apart, as "directories not watched".
- Ansible itself causes it. Without pipelining, which only the containers have, every task makes and removes a directory under the connecting user's `~/.ansible/tmp`, inside the watched `/home`, so a clamonacc restart from the role's handler can lose `/home`. On mail on 2026-10-30 it did, and `clamonacc-mail` mailed the line within a minute.
- Since 1.4.6, a file opened by a process in its own mount namespace, through a read-only bind mount such as a unit with `ProtectSystem=` makes, fails with "Not a regular file" / "Daemon failed to scan" and goes unscanned ([#1878](https://github.com/Cisco-Talos/clamav/issues/1878), opened 2026-10-29); its reporter suspects 1.4.5's quarantine hardening. EPEL 9 ships 1.4.6 (livekit) and Ubuntu 24.04 1.5.4 (dodo, doppelgangerhq.com); prodingus has Debian's 1.4.3. Not yet tested here.
- Since 1.4.5 and 1.5.3, a file clamonacc moves to quarantine is usually quarantined twice, the second copy named `<name> (deleted)`, and listed twice in that minute's mail; the file still leaves its place. A new file gets two scans: fanotify's open event, whose descriptor clamonacc keeps, and with `OnAccessExtraScanning` inotify's close, by path. When the path scan moves the file first, the fanotify scan acts on its descriptor to the unlinked inode, whose `/proc/self/fd` path ends in ` (deleted)`, and copies it into quarantine again; when the fanotify scan goes first, the other only warns "Can't open file … for safe quarantine action". Which goes first is chance, not the directory. In a lima VM, writing 100 EICAR files gave 94 duplicates on Ubuntu's 1.5.4, 71 on upstream's 1.4.6, and none on 1.5.2, 1.4.4 or with extra scanning off; the filesystem, the sticky bit, and a local socket or TCP made no difference. Every clamonacc host here but prodingus (1.4.3) is affected. The hardening (CLAM-2959) deletes a file by first renaming it into a private `.clamav-unlink-<pid>-…` directory beside it, inside the watched tree, which clamonacc's watcher then logs a watch error for. Reported upstream as [Cisco-Talos/clamav#1883](https://github.com/Cisco-Talos/clamav/issues/1883) on 2026-10-30, after nothing there described it.
- doppelgangerhq.com's relay logins had failed since 2026-10-29 04:05; the mail_relay role changed its `null-doppelgangerhq` account in wako's FreeIPA, and they succeeded after. The failures had got it banned by docker-mailserver's fail2ban, in its `postfix` jail: every port on mail timed out from that host while 465 answered from elsewhere. `docker exec mailserver fail2ban-client banned` lists bans, and `fail2ban-client set postfix unbanip <address>` lifts one.
- doppelgangerhq.com has no working outbound IPv6, so Postfix waits 30 s on mail's AAAA before falling back to IPv4 for every message.
- A relay account's first login after the move to wako stamps `krbLastPwdChange` and sets its password to expire after 90 days, though FreeIPA's migration mode is off: null-livekit's and null-pelican's (dodo's, by `mail_relay_account`) times match their hosts' first relay deliveries since 2026-10-26 to the second. The role's next run sets the expiry back to 2038, so its FreeIPA task reports a change once per account after that first login; null-matrix was still at 90 days (2027-01-25) on 2026-10-30. Accounts that have not logged in since the move have no `krbLastPwdChange`; of those, null-lancache, null-mullvad, null-neodingus and null-tinker expired on 2025-12-29. wako's 389-ds access log records neither change.
