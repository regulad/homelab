# aboriginal: homeassistant a podman-compose stack (2026-10-31)

- `homeassistant/home-assistant:latest` had last been pulled at 2026.6.4. Home Assistant tags each monthly release `YYYY.MM` as well as each patch; `2026.6` and `2026.6.4` were one digest, on Docker Hub and ghcr.io alike, so `:2026.6` follows that release's patches. A `YYYY.MM` written unquoted in YAML is a float, and `2026.10` would become 2026.1, so `homeassistant_release` is quoted.
- python-matter-server was archived on 2026-06-23. Its images under `home-assistant-libs` stop at 8.1.0, the one running, which `:8` and `:stable` both name; 8.1.1 and the final 8.1.2 are published only as `ghcr.io/matter-js/python-matter-server`. Its successor, `ghcr.io/matter-js/matterjs-server` (tags `stable`, `X`, `X.Y`), migrates the Python server's data at its first start, with no way back, and runs as UID 1000, so its data directory must be chowned. It ran with no `--bluetooth-adapter`, so the D-Bus mount and `apparmor=unconfined` its compose file carried did nothing. `docker diff` showed it writing only `.pyc` caches and `/tmp/chip_kvs`, so it runs read-only with a tmpfs on `/tmp`.
- Home Assistant installs its integrations' requirements into the image's own environment (`requirements.py` passes pip no target), so it cannot run read-only, and a new container installs them again at its first start: here, hpprinter's `xmltodict` and `flatten_json`, which the image lacks, as it had monitor_docker's `aiodocker` under Docker. That first start took about eight minutes, during which port 8123 accepted connections but answered none.
- host_files' units task started the new `podman-compose@homeassistant.service`, and its restart handler restarted it seconds later, as its compose file had changed, killing Home Assistant mid-start, whose recorder then reported a database not shut down cleanly. A unit the handler restarts is now only enabled by the units task.
- The image's s6 gives Home Assistant 240 s to stop (`S6_SERVICES_GRACETIME=240000`), but Docker and Podman both kill a container 10 s after SIGTERM by default. podman-compose's `down` passes a service's `stop_grace_period` to `podman stop -t`, and systemd's default `TimeoutStopSec` of 90 s must outlast it.
- Every path into Home Assistant's recovery mode logs "Activating recovery mode" (`bootstrap.py`) at WARNING or ERROR, while "Starting in recovery mode" is INFO and is not logged by default. `.HA_VERSION`, in the config directory, is rewritten with the running version when a new release first upgrades the directory. Home Assistant keeps one rotated log, `home-assistant.log.1`, so the Docker run's log was overwritten by the stack's first, cut-short start.
- matter-server's fabric moved into `homeassistant_matter_data`, the name podman-compose gives the stack's `matter_data` volume, created and filled before the stack first started, so the server never started on an empty fabric.
