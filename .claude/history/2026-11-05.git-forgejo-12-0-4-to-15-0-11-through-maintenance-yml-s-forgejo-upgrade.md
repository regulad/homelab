# git: Forgejo 12.0.4 to 15.0.11, through maintenance.yml's forgejo-upgrade (2026-11-05)

- Forgejo's upgrade guide goes straight to the newest release ("upgrade straight to the latest released Forgejo version ... the upgrade procedure will take care of migrations"), and one start ran every migration from 12 to 15. The only floor any release enforces is Gitea 1.5.3's database. `forgejo-upgrade` takes only the long-term support majors that Forgejo's release schedule names: `https://codeberg.org/forgejo/docs/raw/branch/next/release-schedule.json`, an array of `{major, release, eol, lts}`, which Codeberg serves as `text/plain`.
- From 15 the rootless image reads app.ini only at `/var/lib/gitea/custom/conf/app.ini`; 12 still fell back to `/etc/gitea/app.ini`, where the unit bound it, with a deprecation warning. Without the move, 15 would have written a fresh app.ini with `INSTALL_LOCK=false` and an empty database at `data/gitea.db`. The volume had no `custom/conf`; Podman makes it as the bind's mountpoint.
- On 12, the image's `GITEA_APP_INI` names the new path, so `podman exec forgejo forgejo …` read no configuration without `--config=/etc/gitea/app.ini`. The play takes the path from the container's mounts. From 14, the CLI takes a flag's value only as `--flag=value`.
- `forgejo doctor check --all` exits 0 on findings it marks `[E]`, such as regulad/MagiskOnWSA's broken HEAD, so its exit code passes on 12 and 15 alike.
- 229 of the 230 pull mirrors had not synced since 2026-04-13. The `mirror` queue took no flush request at all: `forgejo manager flush-queues` timed out at 60 s, 10 min and 20 s, while its store held about 2 KB. A debug logger added at runtime, `forgejo manager logging add file --writer=<name> --level=debug --expression=lush --filename=/tmp/<file>`, then `logging remove <name>`, logged each queue's flush: every other queue started and finished within a second, and `mirror` logged "Try to flush" and nothing more until the timeout. `FlushWithContext`'s closing debug line always reports `err: <nil>`, as its arguments are evaluated when deferred. It matches Gitea #28919, which upstream answered with the admin UI's "Remove all" on the queue.
- Forgejo has no API for its queues in 12 or 15; "Remove all" is a web form behind a session and CSRF token. `forgejo-upgrade` instead gives each queue a minute to flush and, with Forgejo stopped and its data copied, removes the LevelDB queue store, `data/queues`, which Forgejo makes again at its next start.
- With the store gone, the mirrors resumed on 15: the first run of `update_mirrors`, ten minutes after the start, synced 50 of the 229 overdue, the most one run takes by default, and the next runs take the rest.
- `svc-ansible` is a local Forgejo administrator, made with `forgejo admin user create`, its password generated into SOPS without being printed. The play checks its password login through `/api/v1/user`, with basic auth, before the upgrade and on the new release.
- Forgejo's LDAP login source, `freeipa`, points at the retired `freeipa.home.arpa`; its syncs and lookups fail.
- 15 renames the session and remember-me cookies, so every user signs in again.
