# aboriginal: matter-server on matterjs-server (2026-10-31)

- matterjs-server finds the Python server's node file by computing the compressed fabric ID of the fabric in `chip.json` whose vendor and fabric IDs match its own (0xFFF1 and 1 by default), the name the Python server writes. It keeps that file current as nodes are added or removed, so the Python server can run on the volume again, interviewing afresh any node added since. The entry `2026-10-31.aboriginal-homeassistant-a-podman-compose-stack.md`, saying the migration has no way back, was wrong.
- The fabric it migrated had no nodes: its node file held only `vendor_info`, which the loader warns of ("missing nodes key"). The two TP-Link plugs Home Assistant lists under Matter were commissioned on 2026-06-20 and 22 onto an earlier fabric, whose node file `8757588173134971518.json` was last written on 2026-06-26. Its keys are not in `chip.json`, and restic's two weeklies of aboriginal's root are too recent to hold them.
- The image runs as 1000:1000. Podman's `U` volume option, which podman-compose 1.5.0 passes through, chowns the volume to the container's user at each start, so no one-time chown was needed.
- The image is an OCI manifest, from which Podman reads no `HEALTHCHECK`, so the Dockerfile's healthcheck never runs.
- Its `ping` carries the file capability `cap_net_raw+ep`, and Podman's default capabilities lack `NET_RAW`, so running it fails with EPERM whatever `net.ipv4.ping_group_range` allows, and the API's `ping_node` with it. The container is given `NET_RAW`.
- `LISTEN_ADDRESS` takes a comma-separated list, whose first entry the image's healthcheck script probes. Home Assistant's Matter entry points at `ws://localhost:5580/ws` and connects over `[::1]`.
- podman-compose's `up` keeps running when one of its containers exits, unless given `--abort-on-container-exit`, so stopping matter-server alone kept Home Assistant up while the volume was copied to `/var/backups/matter-server-python`. The stack's restart was then Home Assistant's only one, answering again three and a half minutes later.
- matterjs-server reads `chip.json` only to migrate it, at each start while it is there. Its storage directory, `server-1-fff1`, is named for `VENDOR_ID` and `FABRIC_ID`, not for anything in `chip.json`, so without the Python server's files it starts on its own storage as before, and no longer writes their node file. Its certificates come from the DCL, so the Python server's `credentials/`, the PAA directory its image passed as `--paa-root-cert-dir`, goes with them. `maintenance.yml`'s `matter-server-migration-cleanup` removes those files with the server stopped, then the copy and the Python server's images.
