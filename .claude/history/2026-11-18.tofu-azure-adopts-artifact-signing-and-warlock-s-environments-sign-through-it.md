# tofu/azure adopts Artifact Signing, and Warlock's environments sign through it (2026-11-18)

## Artifact Signing

- **What only the portal does:** an identity validation can only be created in the portal, and it belongs to the subscription, not the account.
  - The portal's New identity button stays greyed out without the "Artifact Signing Identity Verifier" role (`4339b7cf-9826-4e41-b4ed-c7f4505dac08`), which Owner does not include. Assigned on the account, it takes effect after the portal is reloaded.
  - An individual developer's Public validation takes the name and address from the subscription's billing account, which must be of type Individual. It finishes with AU10TIX's ID check and a Verified ID in Microsoft Authenticator.
  - A certificate's subject comes from the validation alone. The profile's name never appears on it.
- **ARM:**
  - `Microsoft.CodeSigning`'s one stable API version is `2025-10-13`.
  - An account's SKU is at `properties.sku.name`, and its top-level `sku` is null.
  - A profile's `properties` hold `profileType`, `status`, `identityValidationId`, `includeStreetAddress`, `includePostalCode`, and its `certificates`.
  - Signing needs "Artifact Signing Certificate Profile Signer" (`2837e146-70d7-4cfd-ad55-7efa6464f958`), assigned on the profile, whose ID is the account's followed by `/certificateProfiles/<name>`.
- **azurerm:**
  - 5.12.0, like 5.14.0, has only `azurerm_trusted_signing_account`, imported by the account's resource ID. Certificate profiles have no resource (hashicorp/terraform-provider-azurerm#27843).
  - `azurerm_resource_provider_registration` imports as `/subscriptions/<id>/providers/<namespace>`.
  - A role assignment on the account imports as the account's ID followed by `/providers/Microsoft.Authorization/roleAssignments/<name>`.
  - With `skip_service_principal_aad_check`, a Signer assignment for a just-created service principal succeeded at the first try, in about 30 s.
- **The Basic tier** allows one certificate profile of each type: `regulad` (Public Trust) and `regulad-test` (Public Trust Test) use both.
- **Discovery without `az`:** `docs/snapshot/azure/lib.sh` signs a client assertion as homelab-tofu and calls ARM and Graph with `curl`.

## Warlock's environments

- **Identity token subjects:** Warlock's repository uses GitHub's immutable subject. `GET repos/<owner>/<repo>/actions/oidc/customization/sub` shows its prefix, `repo:regulad@52430642/Warlock@1463115679`, which an Entra federated credential's `subject` matches followed by `:environment:<name>`.
- **One application per environment:** Azure grants roles to a service principal, not to one of its federated credentials. `warlock-release` and `warlock-testing` are therefore separate applications, each holding Signer on its own profile only.
- **The App's permissions:** creating an environment or a deployment branch policy needs Administration (write), and reading one needs Actions (read). Environments covers only an environment's secrets and variables. Parker added both permissions to the homelab App.
- **integrations/github 6.13.0:**
  - An environment imports as `<repository>:<environment>`, and a deployment policy as `<repository>:<environment>:<policy ID>`. `GET repos/<owner>/<repo>/environments/<environment>/deployment-branch-policies` lists the IDs.
  - Creating a `github_repository_environment_deployment_policy` over an existing policy with the same pattern succeeds, but records policy ID 0. The next plan finds nothing at that ID and creates it again.
  - The repair is `tofu state rm` of that address, then an import block for the live policy. An import block for an address still in state is skipped, and the plan creates the resource instead.
- **Branches:** Warlock's default branch was renamed from `main` to `master` during the adoption. `release` admits `master` and `v*` tags, and `testing` admits `master` and `testing`.

## Probot Settings and environments

Read from probot/settings v5.0.16's `lib/plugins/environments.js`, `diffable.js` and `index.js`:

- **When it syncs:** on a push to the default branch whose commits add or modify `.github/settings.yml`, on a change of default branch, and when a repository is created. Nothing else triggers it.
- **What a sync does:**
  - An `environments:` list is exhaustive. Every environment the file does not list is deleted, and deleting an environment deletes its secrets and deployment policies with it.
  - An environment whose wait timer, reviewers or deployment policies differ from the file's has all its policies deleted and re-created, under new IDs.
  - With no `environments:` key, the plugin does nothing.
- **What it did here:** making `master` Warlock's default branch re-synced `release`'s policies. They were already in place when `tofu/github` first created them, which is how the policy ID 0 entry came about.
- **Why it matters for signing:** an Entra federated credential trusts an environment by name. GitHub creates an environment a workflow names but lacks, with no branch policy, so a deleted environment's restriction on refs is gone until the next apply re-creates it.
- **The resolution:** `tofu/github` is the one owner of Warlock's environments. Warlock's `settings.yml` declares none.
