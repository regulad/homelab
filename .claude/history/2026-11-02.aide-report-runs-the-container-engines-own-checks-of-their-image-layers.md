# aide-report runs the container engines' own checks of their image layers (2026-11-02)

- **No engine re-verifies an extracted layer as it runs.** Image digests are checked at pull, and Docker Content Trust only resolves a tag to a digest at pull. AIDE does not walk `/var/lib/containers`, `/var/lib/docker` or `/var/lib/containerd`, so each engine's own after-the-fact check is what covers them.
- **Podman: `podman system check`, from 5.2.**
  - Without flags it checks everything. Each image layer is rebuilt from its tar-split (`overlay-layers/<id>.tar-split.gz`) and the files on disk, with a CRC64 per file and SHA-256 against the diff ID. Then each layer is mounted read-only and its files' type, uid, gid, size, permission bits and mtime (whole seconds) are compared with the layer's headers, which also finds added and removed files.
  - It does not compare setuid, setgid or sticky bits, xattrs (so capabilities and SELinux labels), symlink targets or device numbers.
  - Its reference data is in the same storage root, as AIDE's database is on the host.
  - Damage exits 125. `--quick` skips the digests from 5.6. `--repair` and `--force` delete images and containers.
  - An unreferenced layer older than `--max` (24h) counts as damage. Directory mtimes changed by some `podman create` setups give false positives (podman#25101).
  - It holds the layer store's write lock through the layer pass, so aide-report runs it at niceness 0 rather than the unit's 19. Lowering a niceness needs CAP_SYS_NICE in the initial user namespace, which root in an unprivileged container lacks; there it stays at 19.
- **Podman 4.9.3 (Ubuntu 24.04)** has no `system check`. Ubuntu's `containers-storage` 1.51 package has the same library check, `containers-storage check`, which exits 1 on damage and, before 1.55, mounts the layers read-write.
  - The package ships `/usr/share/containers/storage.conf`, which Podman reads where `/etc/containers/storage.conf` is missing, as on dodo and ingress. Ubuntu 26.04's Podman depends on the package, so its hosts have run with that file from the start.
  - Installing it broke every Podman command on dodo and ingress: `database graph driver "" does not match our graph driver "overlay": database configuration mismatch`. Podman's database records the driver it was configured with, none on a host that first ran without a storage.conf, and checks it at every command (`checkRuntimeConfig` in `libpod/sqlite_state.go`). An unset driver falls back to the library's default, also none, so it matches. Containers already running kept running.
  - The aide role writes `/etc/containers/storage.conf` on those hosts first, with no driver and `driver_priority = ["overlay"]`. Without a priority, containers-storage 1.51 warns at every command that the driver should be set; the priority picks a driver only for storage not yet initialized.
- **Docker with its own image store:** `docker save` rebuilds each layer from `layerdb/sha256/<chain id>/tar-split.json.gz` and fails on one that no longer matches its diff ID ("could not verify layer data for"). That covers file contents alone, not added files, modes, owners or symlinks.
  - `docker save -o` writes a file beside its target and renames it over it; current CLIs refuse a target that is not a regular file. aide-report streams standard output to `/dev/null` instead.
- **Docker on the containerd image store has no check, and is left a gap.** That store is the default for new Docker 29 installs. dodo's Docker 29.1.3 (2 images) and vkasm's 29.9.2 (52 images, 43 GB, containerd 2.4.2) use it; doppelgangerhq.com's 29.9.2 is on overlay2, which `docker save` checks. authentik, immich, peppercord, mail and aboriginal run no Docker. `docker info` shows it as `DriverStatus` `[["driver-type","io.containerd.snapshotter.v1"]]`. containerd keeps no tar-split, so a snapshot cannot be rebuilt into its layer. Hashing its content-store blobs against their names would add nothing: containerd computes each layer's diff ID as it extracts the blob and aborts on a mismatch, and containers run from the snapshots, not the blobs.
  - Upstream has no check command; its open work is enforcement at read time: dm-verity-backed EROFS layers with IPE (containerd#12081) and fs-verity against malicious corruption (containerd#11105).
  - A check could be built. One way unpacks each image again into another namespace and compares the trees: containerd shares content between namespaces but not snapshots, and its client-side unpack also checks diff IDs. The other streams each blob and compares its entries with the snapshot directories, read-only. `ctr images mount` makes a read-only view under a lease, which `ctr images unmount --rm` removes. Neither was built.
  - moby#54083 reports that this store's unpack does not fsync, which can leave 0-byte files that a re-pull does not repair.
- **AIDE 0.18.6 ignores SIGTERM.** Its handler prints "Caught SIGTERM. Use SIGKILL to terminate" and carries on, so `pkill -x aide` does nothing on Ubuntu 24.04. From 0.19, SIGTERM removes the new database and exits 25 (`SIGNAL_INTERRUPT_ERROR`), which aide-report treats as a failed run.
- **A refresh carries every entry over.** vkasm's refresh against a 258 MB database, still holding containerd's snapshots, ran 22 minutes on AIDE 0.18.6. With the store excluded, vkasm's baseline is 35 MB and aboriginal's 120 MB.
