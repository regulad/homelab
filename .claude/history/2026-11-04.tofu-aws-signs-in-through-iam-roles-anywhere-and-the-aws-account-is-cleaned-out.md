# tofu/aws signs in through IAM Roles Anywhere, and the AWS account is cleaned out (2026-11-04)

- No access key exists for OpenTofu. Signing requests with an asymmetric key is possible only through IAM Roles Anywhere; IAM users have no such option. The trust anchor is a CA whose key was discarded after it issued its one certificate, so the role's trust policy needs only `aws:SourceArn`; a condition on the certificate's subject would add nothing.
- The credential helper, `aws/rolesanywhere-credential-helper`, has no Homebrew formula, so `tofu/aws/tools/go.mod` pins it as a Go tool (`go get -tool …@v1.8.5`). `go -C tools tool rolesanywhere-credential-helper` runs it, but in `tools/`, so every path it gets must be absolute. `GOTOOLCHAIN=local` stops Go from downloading a newer toolchain. The helper needs cgo for PKCS#11.
- The helper opens its `--private-key` file several times: it checks for a TPM key, then for an encrypted key, then parses. Read from a pipe, the later reads find it empty, and v1.8.5 panics with a nil dereference instead of reporting an error. Upstream's request for stdin input is issue #187. The key is therefore kept as encrypted PKCS#8: the helper accepts AES-CBC with PBKDF2 or scrypt. A temporary file then holds only ciphertext, and its password goes in `--pkcs8-password`. `--endpoint https://rolesanywhere.<region>.api.aws` reaches the dual-stack endpoint. Only the `api.aws` names have AAAA records; the `amazonaws.com` ones have none. The session's name is the certificate's serial in hex.
- The state backend needs `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_ENDPOINT_URL_S3` in the environment for OCI, and the AWS provider would read the same variables. Credentials set as provider arguments take precedence over them. A `profile` in the provider block also wins, but aws-sdk-go-base then warns of a "Configuration conflict" on every run. `AWS_ENDPOINT_URL_S3` would also send the provider's own S3 calls to OCI, so the provider names S3's dual-stack endpoint in `endpoints`; a custom endpoint ignores `use_dualstack_endpoint`. The session credentials are ephemeral variables, so neither state nor saved plans keep them.
- An import block's `id` may reference a data source. `aws_caller_identity` supplies the account ID in policy ARNs, and `aws_iam_access_keys` supplies key IDs, which encode the account, so neither is committed.
- `iam get-account-authorization-details` leaves out role and policy descriptions. A policy whose `description` is left unset in HCL plans as a replacement, which `prevent_destroy` refused.
- AWS CloudShell can refuse a long-verified account with "Unable to create the environment. Your account verification is in progress". Other people report AWS Support as the only fix. Trust anchors, roles and profiles can be made in the web console instead.
- The organization was not made by hand. Its trusted access for Identity Center, the Identity Center instance and its only permission set all date from the same few minutes of 2024-08-16, during SageMaker's setup. Deleting the instance (`sso-admin delete-instance`, which the owning account can call on an organization instance) removed its `AWSReservedSSO_*` role and SAML provider. Deleting the organization removed the SSO and Organizations service-linked roles.
- Cleanup findings:
  - AppStream's buckets carry a bucket policy denying `s3:DeleteBucket` to everyone; it must be removed first.
  - Deleting a SageMaker domain deletes its own NFS security groups, but not those of earlier domains or their EFS file systems.
  - AppRegistry deletes the resource groups it manages with the application, a little later.
  - ElastiCache calls recreated its service-linked role after it had been deleted.
  - AWS refuses to delete default RDS parameter and option groups. ElastiCache's `default.iam-user-group` is its own, its `.` impossible in a user-made group's name.
  - The resource-tagging index and Resource Explorer both keep listing deleted resources for a while. Confirm each deletion with the service itself.
  - A per-service sweep missed a launch template and Amazon MQ configurations. `resource-explorer-2 list-resources` caught them, as Resource Explorer was already on with an aggregator in us-east-1.
