# backblaze's state passphrase is rotated and every state version re-encrypted (2026-11-04)

- An agent printed `tofu/backblaze/secrets.auto.tfvars.json`, so the state encryption passphrase was exposed in its session. The new one is 48 characters of `[A-Za-z0-9_-]`, from Python's `secrets.token_urlsafe(36)`, generated 2026-11-04. That provenance lives here because `secrets.sops.json` is JSON, which has no comments.
- OpenTofu stores each key provider's metadata, PBKDF2's salt among it, in the encrypted file under the provider's address (`key_provider.pbkdf2.backblaze`), or under its `encrypted_metadata_alias` if one is set. A new passphrase needs a metadata key of its own. During a decrypt, every method writes into one shared output-metadata map, and a duplicate key fails the whole read. So a fallback aliased to the old name cannot coexist with a new key that still uses the default. backblaze's key provider keeps its labels and stores under `encrypted_metadata_alias = "backblaze-2026-11-04"`, which must never change.
- A state read through a `fallback` method is marked `StatusMigration`, and `PersistState` then writes the state even when nothing changed. A no-change apply therefore re-encrypts the current version (checked in the 1.13.2 source: `internal/states/remote/state.go`, `internal/encryption/base.go`). It touches only the current version, though: the versioned bucket keeps every earlier version under the old key.
- Each stored version was re-encrypted offline and kept its lineage and serial:
  - It ran in two scratch directories with local backends, each initialized before its state file existed, so `init` needed no providers.
  - `tofu state pull`, with the old key as a fallback, was piped into `tofu state push -`, onto a copy of the same snapshot. `state push` reads its source unencrypted, so plaintext existed only in the pipe. Pushing into a missing file instead would bump the serial.
  - The copies were uploaded oldest first with `put-object`, as `application/json`. `tofu plan` with only the new key read the new current version and showed no changes.
  - The originals were then deleted by version ID, as Parker's user. `svc-tofu-state`'s policy withholds `OBJECT_VERSION_DELETE`, so the backend's key cannot purge earlier versions; OCI answers it with `NoSuchBucket`. With the `oci` CLI's session expired, the CLI ran on `tofu/oracle`'s API signing key, given through `OCI_CLI_USER`, `OCI_CLI_FINGERPRINT`, `OCI_CLI_KEY_CONTENT`, `OCI_CLI_TENANCY`, `OCI_CLI_REGION` and `OCI_CLI_AUTH=api_key`, with no config file entry.
- The repository never held a fallback; the old key reached only the scratch directories' environment, from SOPS. `TF_ENCRYPTION` merges over a root's `encryption` block by name (key providers and methods by type and label, a `state` block's `fallback` on its own), so it could also supply a one-off fallback to the root itself.
- Checkouts whose `secrets.sops.json` predates the rotation can no longer read the state, which also breaks the `restic` role's `tf_output` lookup there. Their `secrets.auto.tfvars.json` still holds the old value, and `prepare.sh` refuses to overwrite a copy that differs: delete it, then source `prepare.sh` again once the checkout contains the rotation.
