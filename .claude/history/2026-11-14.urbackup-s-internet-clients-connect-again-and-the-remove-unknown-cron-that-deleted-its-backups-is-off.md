# UrBackup's internet clients connect again, and the remove-unknown cron that deleted its backups is off (2026-11-14)

- UrBackup 2.5's server binds its internet service to 55415, or to `internet_server_bind_port` where that is set. `internet_server_port` is only the port it tells clients to dial, which they take as `internet_server_port_def`. With it set to 55414, the web UI's port, clients reached the HTTP server and never received the challenge packet. It is 55415 again.
- The client reports `"internet_status": "connected"` (`UrBackupClient_cmd.exe status`, in `C:\Program Files\UrBackup`) once its TCP connect succeeds, before authentication. "Error receiving challenge packet" cleans up without changing that status, so Windows shows connected while the server never sees the client. `netstat.exe -ano` filtered to the `UrBackupClientBackend` service's PID shows whether it actually holds connections to 55415. From WSL, the live `debug.log` and `urbackup\data\settings.cfg` are unreadable; some rotated `debug.log.N` files are readable.
- On urbackup, `/etc/default/urbackupsrv` sets `LOGFILE="/dev/null"`, and the journal gets only web logins. The server's databases keep the rest: `backup_server.db` has the client activity logs (`logs`, `log_data`) and every deletion that cleanup makes (`del_stats`); `backup_server_settings.db` has `settings`, where clientid 0 is global and `use_last_modified` dates each change. Both open with `sqlite3 -readonly`. `settings` also holds `internet_authkey`, so queries leave it out.
- Root's crontab, last modified 2026-06-25 and outside this repository, ran `30 */3 * * * urbackupsrv remove-unknown`. That command drops the database row of any image whose file it cannot open and deletes any backup subvolume without a row, and records neither in `del_stats`. Its runs at 06:30 and 09:30 on 2026-09-03 emptied momvertible's, chopbox's and anticlown's folders (folder mtimes 06:30, 09:30 and 09:32). winite's images were gone by its run of 2026-10-28. Cron discarded each run's output, as the VM has no MTA. The entry has been commented out since 2026-11-14, and the storage holds only backups made since then.
- Those runs fell inside a crash loop on Ubuntu's mainline `6.18.0-061800` kernel: kdump booted at 18:33 on 2026-09-02, three minutes after a run, and again at 18:38, a few minutes after the reboot, with no run in between; boots kept ending every few hours until 08:30 on 2026-09-03. The dmesg files kdump saved under `/var/crash/<timestamp>/` are gone. Why remove-unknown found the backups unknown is not known.
- btrfs numbers user subvolumes from 256, so the IDs in `btrfs subvolume list` count every subvolume ever created; only ten existed on `/mnt/urbackup` before 2026-11-14. The RBD image's `create_timestamp` (`rbd info rbd_cmr/vm-111-disk-0`) and the filesystem's birth time are both 2026-07-03, so neither was replaced.
