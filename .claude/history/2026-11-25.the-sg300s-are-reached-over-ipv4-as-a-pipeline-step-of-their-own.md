# The SG300s are reached over IPv4, as a pipeline step of their own

- On VLAN 1 both arawi (`fe80::be24:11ff:fe08:e4e8`, preference high) and the Verizon router (`fe80::1ef4:3fff:fe14:4bee`, preference medium) advertise a default route. The SG300s on firmware 1.4.11.5 take both as equals, `ND> ::/0 [0/0]`, ignoring the preference, and a configured `ipv6 default-gateway fe80::be24:11ff:fe08:e4e8%vlan1` added no static route beside them. switch45f304's replies to tailnet ULAs then left through the Verizon router and were lost, while switch070e26's did not (2026-11-25), so tailnet access to the switches over IPv6 depends on which router each picks.
- `bin/with-switch-keys` exports `ANSIBLE_LIBSSH_PROXY_COMMAND='nc -4 %h %p'`: libssh connects to the switch's name, so `~/.ssh/known_hosts` still pins its key by name, while the TCP connection goes over IPv4 to the A record. `network_cli` passed libssh no `ansible_libssh_proxy_command` from inventory variables, while the environment variable reached it.
- The pipeline's `ansible-hardware` had never reached the SG300s: it ran without `with-switch-keys`, whose throwaway agent holds only their key. `ansible-hardware--switches` runs them inside it (`WRAP`), and `ansible-hardware` leaves the `ciscosmb` group out.
- An SG300 refused SSH with a connect timeout for a few minutes after a console session and a configuration restore, then accepted it in about 15 s.
- `copy startup-config running-config` on an SG300 merges the startup configuration into the running one: a line only the running configuration held, such as a hand-entered `ipv6 default-gateway`, stays until the `ciscosmb` role's removal pass or a reboot.
