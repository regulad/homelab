# PepperCord's MongoDB from 5.0 to 9.0, a major release per run, and its Redis on 8's tag (2026-11-16)

- Both hosts' data was at FCV 4.4 under MongoDB 5.0.31: it was created on 4.4, and nothing had raised the FCV since. A 6.0 binary needs FCV 5.0, so `mongo-upgrade` raises the FCV to the running release before it changes the image.
- Docker Hub's tags drift from their release series. `mongo:5` had stopped at 5.0.31, 21 months old, while `mongo:5.0` had 5.0.33. `mongo:8` is no longer 8.0 but a later minor release, whose FCV is its own, so podman-auto-update following a major's tag would cross an FCV boundary by itself. `mongo:9` and `mongo:9.0` were the same image. The compose file therefore tags a release series, `mongo:9.0`.
- `mongosh` (2.3.8) is in the 5.0 image too, so one shell works at every step. `setFeatureCompatibilityVersion` takes no `confirm` on 5.0 and 6.0, and requires `confirm: true` from 7.0 on. 9.0 upgrades from 8.0 directly (or from 8.3). The 6.0 upgrade pages are only in the legacy documentation, in `mongodb/docs`'s `v6.0` branch.
- MongoDB's driver table lists PyMongo 4.18 and later as fully compatible with 6.0 through 9.0. An audit of PepperCord's MongoDB calls found nothing in the 6.0–9.0 compatibility changes: it uses only find, find_one, update_one, replace_one and delete_one on `user` and `guild`, with no aggregation or admin commands.
- PepperCord's `/health` does a real read, upserting write and read back on its own `user` document, so a 200 proves writes work. It answers 503 until the Discord gateway is ready, and while mongod is down it blocks for PyMongo's 30 s server-selection timeout before answering 500. The play's waits allow 40 s per check and look for `"status": "ok"`.
- The hosts' 8 GB root disks hold about two MongoDB images: 805 MB for 6.0, 955 MB for 8.0 and 1.14 GB for 9.0. With the 5 and 5.0 images still there, cordpepperer's pull of `mongo:7.0` failed with "no space left on device" while unpacking `mongos`. That was before the play stopped the stack, so nothing went down. The play now removes MongoDB's images other than the running and declared ones before each pull.
- The `db` volume takes about 500 MB on disk while its databases hold 2–4 MB, mostly WiredTiger's journal and diagnostic data, so each step's copy was 400–500 MB.
- After an image change, the stack's first start spends about 35 s pulling, and a probe in that window finds no containers or an exited mongo. `NRestarts` and the unit's journal tell such a probe from a crash loop.
- Redis's tag moved from `8.4-alpine3.22` to `8-alpine`, and 8.10.3 read 8.4's data.
- PepperCord removed its own `docker-compose.yml`. Its README links to this repository's `ansible-generated/files/shared/peppercord/docker-compose.yml`, which is now the only one.
