# snapd's AppArmor cache is a tmpfs (2026-11-10)

- **`skip-cache` in `/etc/apparmor/parser.conf` does not reach snapd.** snapd compiles its snaps' profiles with its own `apparmor_parser`, `/snap/snapd/current/usr/lib/snapd/apparmor_parser`, configured inside the snapd snap, and writes their cache to `/var/cache/apparmor`, which AIDE does not walk. On aboriginal (snapd 2.77.1+ubuntu26.04.2) the cache came back as 29 files, 1.2 MB, under `f6da0254.0`.
- **`snapd.apparmor.service` loads the snaps' profiles at each boot from that cache:** `ExecStart=/usr/lib/snapd/snapd-apparmor start`, with `DefaultDependencies=no`, `Before=sysinit.target`, `After=apparmor.service` and `RequiresMountsFor=/var/cache/apparmor /var/lib/snapd/apparmor/profiles`.
- On a host with snapd (aboriginal and vkasm), the `aide` role mounts a tmpfs there, `var-cache-apparmor.mount` (`mode=0755,noexec,nosuid,nodev`, wanted by `local-fs.target`), which `snapd.apparmor.service` thereby requires, so no cache outlives a boot and snapd compiles each profile at boot from its source in `/var/lib/snapd/apparmor/profiles`, which AIDE watches. The cache on disk is removed first; elsewhere the directory is removed as before. A changed unit takes effect by a remount, which keeps what the tmpfs holds; a restart would empty it under the loaded profiles.
- The aide play gathers no facts, so the role asks `findmnt --mountpoint /var/cache/apparmor` what holds the directory before removing it.
