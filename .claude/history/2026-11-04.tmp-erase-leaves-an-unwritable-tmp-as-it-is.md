# tmp-erase leaves an unwritable /tmp as it is (2026-11-04)

- **doppelgangerhq.com's `/tmp` on the root filesystem is immutable** (`chattr +i`), beneath the tmpfs of `tmp.mount`, which was linked there by hand on 2025-11-01. The directory and what it holds, the empty `.X11-unix`, `.ICE-unix`, `.XIM-unix` and `.font-unix` that systemd-tmpfiles' `x11.conf` makes, date from that day; no record on the host says who set the attribute. Nothing can be added to or removed from an immutable directory, by root either, so `tmp-erase.service` failed when the host booted on 2026-11-04, on `find`'s EPERM for each of the four. `tmp.mount` mounted anyway, as `Wants=` does not hang on the service's result.
- **Reading beneath a mount** without touching the host's: `unshare -m --propagation private sh -c 'umount -l /tmp && lsattr -d /tmp'` unmounts it in a namespace of its own alone.
- **An unwritable `/tmp` is skipped.** Root's `access(2)` for writing fails on an immutable inode, as on a read-only filesystem, so `test -w /tmp` fails there; the unit's `ExecCondition=/usr/bin/test -w /tmp` then skips it, which an `ExecCondition=` exiting 1 to 254 does without marking the unit failed (systemd 243 and later). Such a `/tmp` can hide nothing written since it became so. A changed unit has its last failure cleared (`systemctl reset-failed tmp-erase.service`), as the next boot runs it again.
