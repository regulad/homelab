# aboriginal: nextcloud a podman-compose stack; its LDAP on wako (2026-10-31)

- `nextcloud-ca` was the stock `nextcloud:32-apache` of December 2025 (32.0.3) with two steps more, `COPY ipa-ca.crt /usr/local/share/ca-certificates/` and `update-ca-certificates`. The stock image with the host's `/etc/ssl/certs` bound read-only replaces it, as for ldap-auth and uptime-kuma: the bundle `ca_trust` builds holds the HOME.ARPA CA, wako's, and the rest, and leaves out the roots it distrusts, which the image's own bundle still trusts. Nextcloud's own HTTP client uses its bundled CA list and the certificates `occ security:certificates:import` adds, of which there were none; PHP's LDAP and OpenSSL use the system bundle.
- The image declares `VOLUME /var/www/html`, so Docker had given its code an anonymous volume. podman-compose's `down` and `up` would give each new container a fresh one, and the code is now the named `nextcloud_html`, filled from the anonymous volume.
- Docker's DNS answered for the cache container's `hostname: redis`, the host `config.php` names; aardvark-dns answers only for names and aliases, so the cache service has `redis` as an alias.
- podman-compose 1.5.0's `--dry-run` still creates the project's volumes and network (`podman volume inspect … || podman volume create …`), labelled as its own; the copies went into those empty volumes.
- The old compose file's php-fpm pool did nothing, as the Apache image runs PHP as an Apache module and has no php-fpm, nor did its blkio weight, with `vda` on `none` or mq-deadline rather than BFQ.
- Docker had never pulled `mariadb:10-jammy` again since 10.11.6; the move brought 10.11.19.
- The data directory, `/opt/nextcloud`, was renamed to `/srv/nextcloud` on the same btrfs, so that `/opt/nextcloud` holds the stack and the project's name stays `nextcloud`.
- Its `.htaccess` lacks the section `occ maintenance:update:htaccess` writes, so `front_controller_active` is unset and its links go through `index.php`; `/login` answers 404 and `/index.php/login` 200. It was so under Docker as well.
- After the repoint, `occ ldap:check-user` called each of the 9 users gone and marked them as remnants: it reads the mapping's old DN, which wako does not have. `occ ldap:search` under the new base found them all by `ipaUniqueID`, which `ipa-migrate` kept, and wrote their new DNs into `oc_ldap_user_mapping`; `check-user` then found each and cleared its mark.
