# tinyxnb reports to Sentry from its tagged builds

- `tofu/sentry`'s `tinyxnb` project (platform `dotnet`) takes both of tinyxnb's programs, the thumbnail handler and `xnb2png`. Only a tag's build compiles the DSN in, so pull requests, tests and builds from source send nothing. Sentry is on by default and `DO_NOT_TRACK` turns it off; empty, `0` and `false` count as unset, as Warlock reads it. Scoop has no rule on telemetry, so the bucket's manifest says how to opt out in its `notes`.
- A run is one program start: the handler's per-`dllhost.exe` start, or one `xnb2png` invocation. Each gets a random ID that is set on every capture and never stored, in place of the installation ID the .NET SDK would persist. Inside `dllhost.exe` the handler turns off the SDK's process-wide integrations, as the process isn't its own.
- The repository's `SENTRY_AUTH_TOKEN` (`tofu/github`, from `tofu/sentry`'s `org-tokens.sops.yaml` key `terraform-tinyxnb`) serves the release workflow's two Sentry jobs: debug files, and the release with its commits and deploy.
- upload-artifact keeps several paths below their common ancestor, so the `debug-files` artifact holds each PDB at its publish directory (`XnbThumbnail/bin/Release/net8.0-windows/win-x64/publish/…`), not at its root. 26.11.25's upload failed on `debug-files/*.pdb` and its PDBs went up by hand; tinyxnb's f2b5a6d uploads the directory, which sentry-cli scans recursively.
- The `sentry` CLI that dotfiles installs (0.50, the TypeScript one) is not the Rust `sentry-cli` the workflows pin: it uploads debug files with `sentry debug-files upload <dir>`, taking the organization and project from `SENTRY_ORG` and `SENTRY_PROJECT`.
- Excavator in `regulad/scoop-regulad`, which updates the bucket every four hours, had been off since June: GitHub turns off a scheduled workflow after 60 days without repository activity. Once it was back on, it took tinyxnb to 26.11.25. Its `checkver` patterns for `retry` and `nssm` match none of their latest releases.
