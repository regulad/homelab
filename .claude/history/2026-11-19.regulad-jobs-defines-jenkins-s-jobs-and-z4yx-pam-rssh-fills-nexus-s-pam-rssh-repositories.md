# regulad/jobs defines Jenkins's jobs, and z4yx/pam_rssh fills Nexus's pam-rssh repositories (2026-11-19)

- **regulad/jobs's seed workflow drives Jenkins from GitHub Actions.**
  - On each push to `main`, `seed/apply.sh` signs in as svc-jobs with its password, keeping the session cookie that Jenkins's CSRF crumb is bound to. It writes the seed job from `seed/config.xml` (`createItem`, or the job's `config.xml`), builds it with `buildWithParameters?COMMIT=<sha>`, and follows the queue item's `Location` to the build.
  - `seed/config.xml` is the XML a Job DSL dry run in the script console printed for the seed, so it matches the installed plugins.
  - The repository has no root `Jenkinsfile`, so the `regulad` organization folder ignores it.
- **Credential scope:** a credential in the system store with `scope: GLOBAL` is every job's. That includes every `Jenkinsfile` the `regulad` folder builds, and pull requests whose authors have write access, which the folder trusts. `SYSTEM` hides a credential from all jobs, and domains limit nothing.
  - Configuration as Code fills `${name}` into its Job DSL scripts too, so a folder can be defined there with credentials in its own store (`folderCredentialsProperty`), which only its items can use. `z4yx` is defined that way.
  - regulad/jobs defines only the jobs inside a folder. Its seed would otherwise rewrite the folder without its credentials.
- **A folder that Configuration as Code creates at a start isn't loaded.** Jenkins builds its job table from the directories it finds at startup, and that table replaced the new folder: it was on disk, but `Jenkins.instance.getItem('z4yx')` was null, and nothing was logged. `POST /configuration-as-code/reload` loaded it, without a restart.
- **FreeIPA expires an administrator's password even in the `user_add` call that sets `krbpasswordexpiration`,** so the jenkins role sets each service user's expiry after its password, on every run. Jenkins's LDAP realm accepted the expired password, as an LDAP simple bind still succeeds.
- **Jenkins learns a pipeline's own parameters only from a run.** Before its first run, `z4yx/pam_rssh` had no `DRY_RUN`, and a first build would have uploaded. Its Job DSL declares the parameter as well.
- **The Groovy sandbox,** without approvals:
  - Script security's generic allow list has `JsonSlurper` and its `parseText`, but not `JsonSlurperClassic`. Its lazy maps can't outlive a step, so the pipeline parses inside `@NonCPS` methods that return plain values.
  - `=~`, `==~`, `Matcher.matches()` and `MatchResult.group(int)` are allowed.
  - The script console doesn't know `@NonCPS`; drop it to test such a method there.
  - `jenkins/inbound-agent` has `curl`, `git` and coreutils, but neither `jq` nor Python.
- **Matching uploads:** GitHub's releases API gives each asset's `digest` (`sha256:…`), and Nexus's assets API each asset's SHA-256, so the pipeline uploads only what Nexus lacks, and checks each download against its digest first.
- **Signatures:** an APT hosted repository serves `InRelease` only once it holds a package. Each of the eight with packages verified with `gpgv` against its own key from `keys`. The YUM group's `repomd.xml.asc` verified against `pam-rssh-rpm.asc`.
- **Pushing a workflow file through `gh`'s OAuth token is refused** without the `workflow` scope. Over SSH, as homelab pushes, it isn't. The Settings app applied `.github/settings.yml`'s description and topics on the first push.
