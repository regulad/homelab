# ingress's IPv6 leaves through the upstream router, and cloudflare-ddns publishes its own address (2026-11-06)

- ingress.regulad.xyz's AAAA, which every vhost CNAMEd to it inherits, was arawi's LAN GUA. cloudflare-ddns v1.18.0 reads `IP6_PROVIDER`; it ignored `IPV6_PROVIDER` and fell back to `cloudflare.trace` (its startup log lists each default it takes). arawi's "weird state-tracking" outbound NAT rule has no address family, so its IPv6 half rewrites the LAN's TCP leaving through arawi to arawi's own GUA, which trace reported. ingress now uses `local`, the kernel's source-address choice, and filters out fc00::/7. `local.iface:` returns every global address on the interface, the ULA included.
- pfSense's radvd adds `route ::/0` to every RA interface. networkd 255 ignores it; from 256 on it routes it at metric 512 for high preference, outside `UseGateway=`'s reach. ingress's 26.04 upgrade (systemd 259) brought that route in, ahead of its static route through the upstream router at 1024. That route is now at 256. `RouteDenyList=::/0` would deny every route option, tailscalerouter's too.
- arawi's antispoof rule (tracker 1000001471) drops the LAN's /64 arriving on LAN2. "Allow LAN to any via LAN2" overrides it for SYNs, but no `flags S/SA` rule passes a SYN-ACK, so replies to inbound IPv6 sent through arawi died there.
- doppelgangerhq.com is the outside-equivalent vantage for the homelab's IPv6; the wahlecloud instances get their replies over the tailnet. The CR1000B forwards inbound IPv6 to ingress, but not to arawi, whose web interface pf admits only from the LAN. After the fix, git.regulad.xyz answered 200 over IPv6 from doppelgangerhq.com with ingress's Let's Encrypt certificate.
- dodo still sets the ignored `IPV6_PROVIDER`, and its default publishes its own EUI-64 only while it runs systemd 255; on 26.04 it needs the same two changes. `DELETE_ON_FAILURE` is not an updater setting either.
