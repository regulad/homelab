# PepperCord's Redis removed from its stack, as the bot no longer uses it (2026-11-16)

- PepperCord had built a Redis client at startup since 2025-11-22 without ever sending it a command. redis-py connects only on a client's first command, so the bot never opened a connection. Release 2b8025b drops the client and no longer reads `PEPPERCORD_CACHEDB_URI`, which had been required: a missing variable was a KeyError at startup. Replacing Redis with Valkey had been the plan until then.
- podman-compose 1.5.0's `down` removes the containers of services that have left the compose file only with `--remove-orphans`, which the shared `podman-compose@.service` does not pass. The redis container therefore outlived the restart, and podman-restart.service started it again at the next boot, as its restart policy was `always`. Its container, volume and image were removed by hand on both hosts. The unit is shared by six stacks on four hosts, so adding the flag there would restart all of them.
- Uptime Kuma's notifications for the two bots' `/health` go to prodingus's webhookd, whose hooks `pct reboot` the container. Any restart of the stack that fails a check therefore reboots the container. The `host_files` restart at 04:23 EST had both containers rebooted (`vzreboot` by root@pam) 13 s after the stop began. Earlier reboots at 03:06, 03:07 and 03:17 were recorded the same way. None landed during the `mongo-upgrade` runs, though each stopped its stack for 30 to 60 s; `mongo-upgrade`'s header now says to pause the host's monitor.
- Deploys lost to these reboots: PepperCord's deploy hint at 08:16 UTC got a 200 from peppercord's webhookd, whose hook starts podman-auto-update with `--no-block`. The reboot at 03:17:09 EST then cut that run off, and the timer's run after boot started before podman-compose had created the containers, so it found nothing to update. A lost deploy waits for the next daily podman-auto-update run, which Parker accepted. An `After=` ordering would not help, as `podman-compose@.service` is `Type=simple` and counts as started before its containers exist.
- `sops set --value-stdin` (sops 3.13) replaces one value of a SOPS file without the new value appearing in a process listing; `sops -d --extract` reads it back for a check.
