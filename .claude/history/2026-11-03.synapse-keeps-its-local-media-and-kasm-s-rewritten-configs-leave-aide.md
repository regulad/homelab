# Synapse keeps its local media, and Kasm's rewritten configurations leave AIDE (2026-11-03)

- **Synapse's media retention deletes media, not a cache.** `media_retention.local_media_lifetime`, carried over from VM 107 at 14 days, runs hourly. Through `_remove_local_media_from_disk` (Synapse 1.164.2) it removes each file and its thumbnails and calls `delete_url_cache_media`, which deletes the media's rows from `local_media_repository` and `local_media_repository_thumbnails`, so the media is gone from Synapse. The S3 storage provider is never told, and its copy stays in `synapse-media` with no row referring to it. The logs showed 57 to 147 deletions a day from 2026-10-31. `remote_media_lifetime` is unaffected in kind: remote media is fetched again from its server.
- **The S3 provider never removes local copies.** With `store_local`, `store_remote` and `store_synchronous`, Synapse writes each upload to `media_store_path` and the provider copies it to the bucket within the request; reads go to the local file first, then the provider. The provider's tool for evicting local copies is `s3_media_upload` (`update` with a last-access age, then `upload --delete`), in Synapse's venv at `/opt/venvs/matrix-synapse/bin`. Media whose local file is gone but whose row remains is served from S3: on 2026-11-03 the bucket held 46,823 objects under `local_content/`, `local_media_repository` 51,767 rows, and the media store 7,707 files.
- **Synapse 1.164.2 logs "Metric named cache_lru_cache_… already registered" errors at every start,** 27 lines from `notify_interested_services`; they appeared at the 06:08 start after its upgrade too.
- **AIDE 0.18 drops a file's hashes when it changes between being found and being read.** `calc_hashsums` (`src/do_md.c`) compares the `fstat` of the opened file with the `lstat` from the walk and, if they differ, logs a warning to standard error and records no hashes, which aide-report does not keep. In a full run the hashing trails the walk by minutes. Kasm writes its agent's and gateways' `*.app.config.yaml` anew, each under a new inode, every 30 to 100 seconds, with the same contents, so the baseline and most checks hold no hashes for them, and aide-report cannot tell them rewritten with what they held. They are excluded on vkasm. `aide -p f:<path>` shows the rule a path gets, and `aide --check --limit <regex> -L debug` how one entry was read.
