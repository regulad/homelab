# mail's user Sieve scripts get only the extensions they use (2026-11-06)

- `config/dovecot.cf`, deployed by host_files, sets `sieve_extensions = copy imap4flags`, the extensions the one personal script (regulad's) requires. It grants the extensions docker-mailserver's own scripts use beyond those (`vnd.dovecot.pipe`, `imapsieve`, `fileinto`, `special-use`, `environment`, `vnd.dovecot.imapsieve`) to global scripts only. ManageSieve on 4190 now advertises `"SIEVE" "imap4flags copy"`.
- docker-mailserver copies `config/dovecot.cf` to `/etc/dovecot/local.conf` only as it sets up a new container; its change detector does not watch it. Changing it needs a restart of `mailserver.service`.
- In Dovecot 2.4 a space-separated boolean list replaces the whole list, and a `{ key = yes }` block merges into it. `doveconf -c /dev/stdin`, fed `dovecot_config_version`, `!include /etc/dovecot/dovecot.conf` and a candidate, previews a change read-only.
- Pigeonhole enables what `sieve_global_extensions` lists and keeps it from user scripts. Global scripts, IMAPSieve's administrator scripts among them, get both lists. ManageSieve advertises only the non-global ones. The docs give the global list's default as `sieve_extensions`, but in the source it is empty. The IMAPSieve plugin enables `imapsieve`, `vnd.dovecot.imapsieve` and `environment` whatever the lists say.
- A docker-mailserver feature turned on later with a script of its own may need a global extension: `MARK_SPAM_AS_READ`'s requires `mailbox`, `SPAM_SUBJECT`'s `variables`.
- `doveadm sieve list -A` fails on mail because the LDAP userdb cannot list users; personal scripts were found under `/var/mail` instead.
