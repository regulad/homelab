# Agent cheat sheet: `regulad/homelab`

Read this first. This repository makes a home Proxmox cluster and an OCI tenancy
declarative: OpenTofu for machines, Ansible and Podman Quadlets for what runs on
them. Parker supervises and approves.

- **Plan and status:** [`.claude/PLAN.md`](.claude/PLAN.md) has the goals, phases, and each phase's current status.
- **History:** [`.claude/history/`](.claude/history/) records what was done, one file per entry, each a title and the technical findings likely to help a later session. Add new history there, as a new entry committed with the work it records ([Conventions](#conventions)), and nowhere else.
- **Directory detail:** each `README.md`, starting with [`tofu/oracle/README.md`](tofu/oracle/README.md).
- **Platform:** Unix-like systems only: Linux (WSL counts) or macOS, with a POSIX shell. Native Windows is not supported; write scripts and documented commands for `sh`/`bash`, never PowerShell or batch.
- **Managed elsewhere:** workstation configuration lives in [`regulad/dotfiles`](https://github.com/regulad/dotfiles); never add or change it from this repository. The tailnet's policy file, DNS and federated identities are `tofu/tailscale`'s; [`regulad/tailscale-acls`](https://github.com/regulad/tailscale-acls), which held the policy and DNS before, is to be retired.

Where this file and the plan disagree, this file wins.

## Priorities

- **IPv6-first.** The homelab is IPv6-first: wherever a service, route or resolver has an IPv6 address, configure it, and treat IPv4 as the fallback rather than the default. The LAN's GUA prefix rotates, so where a peer's address is pinned (trusted proxies, allowlists, LAN-detection lists), use its ULA or reserved IPv4, never its GUA. ingress's Caddy reaches aboriginal over IPv4, as DNS can't pick out the ULA.
- **Encrypted at rest.** Every disk that holds the homelab's data is encrypted at rest, and no key that opens one is stored in the clear on any disk. A physical disk gets dm-crypt (LUKS2) directly on its block device, below the filesystem, opened with discards passed through so that TRIM still reaches the drive; this reveals which blocks are free, a leak accepted for the drive's health. A network block device is covered by what stores it: Ceph RBD and CephFS by the encrypted OSDs, and OCI's volumes by Oracle's encryption at rest. Not yet met on prodingus's boot NVMe, which holds `local-lvm` (the VMs' EFI and TPM state, and vkasm's disk) and the Ceph monitor's store, where the OSDs' keys are kept. That disk is Parker's to encrypt, at the machine: don't plan or start it. LUKS keys stay sealed to PCR 7: the software vTPM is to move to a secure enclave later, which the binding is for, so don't argue for unbinding.
- **DRY.** Derive values from their single source instead of restating them: compose from OpenTofu state or outputs where possible, then from another host's declared variables, and write a literal only where no source exists.
- **No security theatre.** Add a measure only for the risk it actually reduces. Something that looks like hardening but defends nothing only causes confusion, so leave it out. The textbook case is a restic password per host: every repository key opens the same master key, so per-host passwords protect nothing that one shared password does not. What limits and revokes a host's access is its own B2 key.

## Hard rules

1. **Approval for every mutation.** Never change infrastructure or state without Parker's explicit approval in chat for that specific action; an earlier approval never carries over. This covers `tofu apply|destroy|import`, `tofu state rm|mv|push`, `ansible-playbook` without `--check`, `pct|qm destroy|stop|set`, `pvesh set|create|delete`, `ceph config set` and other Ceph changes, `podman rm|stop`, `oci ... delete|update`, `aws` calls that create, change or delete, and `ask deploy` and `ask smapi` create, update and delete calls. Local file edits, SOPS encryption, validation, and read-only plans need no approval.
   - Claude Code's auto-mode check judges each apply against Parker's latest message, and refuses a plan made and applied in one command. Make the saved plan, show it, and apply it in a separate command. Do the commits and checks first, then ask, naming the exact command, so that the apply is the first command after his grant. With several applies, expect to ask again for each one after the first. If the check refuses, stop and ask; never retry or work around it.
2. **Read-only discovery.** Discover with reads only. The OCI API key and session token and the `gonkputer` `root@pam` API token and root SSH are read/write, so rule 1 is the safeguard there. Never create or broaden credentials yourself.
   - Appraise a fleet-wide property, such as Tailscale's DNS or accepted routes, from what the repository declares (host_vars, group_vars, role defaults, OpenTofu) and the tool's documented defaults, and say which parts are defaults. Never fan ad hoc `ansible all -m command` out over the fleet: parallel `pct` sessions overrun prodingus's SSH. Probe one host, and only for a fact the repository cannot give.
   - A probe writes nothing on the host. Start Python as `python3 -I -B`, since `-I` alone still writes `__pycache__`, which AIDE reports. Keep scratch in a `tempfile.TemporaryDirectory()`, and never run a tool under a made-up `HOME`, which it creates: `HOME=/nonexistent go version` creates `/nonexistent/.config/go/telemetry`. Unset `LC_ALL` before running AIDE: Ansible passes the controller's locale, and AIDE exits 20 on a config script's warning about it.
3. **No installs.** Never install tools, Python packages (`uv sync`, `uv tool install`), pre-commit hook environments, or OpenTofu providers (`tofu init` downloads) without Parker's approval for that install. He manages tools declaratively; `uv` is the Python/tool manager.
4. **No secrets in git; the repository is public.** Never commit tokens, keys, state, plans, `.terraform/`, plaintext `*.tfvars`, or discovery output. Sensitive values that must be committed go in SOPS-encrypted `*.sops.*` files (age recipients in `.sops.yaml`).
   - OCIDs owned by our tenancy or compartments link resources to the tenancy, so they stay encrypted, including router next-hop IDs. Verified Oracle-defined OCIDs may be plaintext as entries in a module's `platform_image_ids` or `backup_policy_ids` map, keyed by their exact Oracle name. Verify ownership before publishing an unfamiliar OCID.
   - AWS account IDs, and the ARNs that carry them, are plaintext: AWS does not consider them secret.
   - OAuth client IDs are plaintext everywhere, Google's and Entra's alike; their client secrets stay encrypted. Each is written once, in its provider's root, which exports it as `oauth_client_ids`.
   - GUA IPv6 `/64` prefixes stay encrypted; derive host addresses and enclosing prefixes from them. IPv4, ULA and Tailscale ranges, IPv6 host suffixes, and SSH public keys are plaintext, as are publicly known GUAs such as public DNS resolvers, each listed in the `no-gua-ipv6` hook's allowlist. Printing a GUA in a session is fine, as GUAs are public anyway (certificate transparency logs, DNS); only committing one is forbidden, so build no redaction around them.
   - Password hashes may be plaintext when salted and from an adaptive algorithm such as bcrypt. Private keys, including WireGuard keys, stay encrypted.
5. **Don't invent facts.** Discover with read-only commands, keep raw output in the gitignored `docs/snapshot/`, and ask about anything unknown. Verify provider and tool details (resource names, import ID formats, flags) against current docs. Record what a check showed and when ("unreachable on 2026-10-18"), never a pattern drawn from one probe. Ask before describing a host's availability, role, cluster membership or internet exposure.
6. **Stop and ask** when a plan shows any destroy or replace, when an Ansible `--check` shows unexpected changes on a production host, or at an auth or permission wall.
7. **Pin everything:** providers with a committed `.terraform.lock.hcl`, Ansible collections in `requirements.yml`, and container image tags (never `latest`, except where upstream publishes no version or channel tag besides dated or per-commit builds).
8. **Commits only when Parker asks.** The one exception: an agent working in a worktree of its own commits on that worktree's branch before applying, because alock applies only from commits (see [Parallel agents](#parallel-agents)); what reaches master is still Parker's call. Keep each one small and single-purpose, with a conventional-commit message, `<type>(<scope>): <summary>`. The scope names what the commit changes: a host (`aboriginal`), an OpenTofu root (`gonkputer`), a role (`quadlet`), an Ansible stage (`ansible-generated`), a document (`agents` for this file's conventions, `history`, `todo`), or `orchestration` for how agents work together, such as alock and worktrees.
9. **Secrets in output:** regulad/skills' rules on printing and rotating secrets apply. In this repository:
   - Learn a SOPS file's shape from its key paths and value types alone: `sops decrypt --output-type json <file> | jq -c 'paths(scalars) as $p | [$p, (getpath($p) | type)]'`.
   - Read one value with `sops decrypt --extract '["<key>"]'` straight into the pipe or file of the command that uses it, never onto the terminal. To check a property of a secret, print only what a parser picks out of it, such as a URL's host or a key's DER field offsets, never a substitution that lets unmatched text through.
   - Search hosts with `grep -rl`, file names only, never `grep -rn` over `/etc` or `/root`. Keep `no_log` on tasks that pass secrets, drop `--diff` from a check run whose change removes a secret from a file, and list inventories with `ansible-inventory --graph`: `--list` and `--host` print the SOPS variables decrypted.
   - Filter service logs by the exact message wanted, never by words such as cookie, token, key or password.
   - Parker has ruled some secrets low-value: an exposure of one is reported, but needs no rotation and blocks nothing. They are notification webhooks (dodo's cloudflare-ddns Discord webhook), Wings node tokens, Nexus's pull-only `knownguest` token, which is shared on purpose, and a truncated prefix a service logs. For a partial key leak, map what printed onto the key's DER fields, printing offsets and booleans only, and let him rule.

This model guides where new work goes. The repository itself is the
authoritative state: where they differ, the repository wins, and changing the
model is Parker's decision.

- **OpenTofu** owns which machines exist, plus the Proxmox cluster-wide settings its provider supports. It never manages containers or in-guest files.
- **cloud-init**, set by OpenTofu, fully configures every Proxmox VM that can boot with it. Its whole setup lives in a cloud-init vendor file, a snippet under `tofu/gonkputer/snippets/`, so it needs no SSH and no Ansible.
- **Ansible** owns everything inside the other guests and the hardware hosts, and the Proxmox and Ceph cluster-wide settings OpenTofu cannot manage, applied on the nodes. It reaches LXC containers through the `community.proxmox.proxmox_pct_remote` connection plugin, which runs `pct` on their Proxmox node over SSH, so the containers need no SSH of their own. Everything else it reaches over SSH directly. Service lifecycle lives in Ansible data (`host_vars`), never in OpenTofu state.
- **Two Ansible stages, two inventories:** `ansible-hardware/` configures the hosts OpenTofu cannot create, listed by hand in its `hardware.yml`, after `tofu/backblaze` and before the other OpenTofu roots run; the one OpenTofu output it reads is `tofu/backblaze`'s `restic`. `ansible-generated/` configures the hosts OpenTofu creates or adopts, from OpenTofu state through the `cloud.terraform.terraform_state` inventory plugin, after. `tofu/authentik`, which configures authentik through its API, runs after `ansible-generated` has brought authentik's stack up. Neither stage reads the other's inventory. Roles both apply live in `ansible-common/roles/`, and plays both run in `ansible-common/playbooks/`, which each stage's `site.yml` and `maintenance.yml` import before their own plays, all but `aide-refresh.yml`, which both import last; anything used by one stage stays in that stage's folder.
- **Separate roots per provider** limit blast radius. Cross-root sharing goes through explicit outputs, or through `tofu/shared` for constants.

## Everyday commands

From the repository root, in bash or zsh:

```bash
go tool task oracle:init                          # once per clone; downloads providers
go tool task oracle:plan                          # a saved plan; its exit code: 0 no changes, 2 diff, 1 error
pre-commit run --all-files                        # among its hooks, tofu fmt and tofu validate for every root
```

- **Applies, and every `site.yml` run, go through `go tool task`** ([Tasks](#tasks)), so that each apply propagates to its dependents. `.claude/settings.json` denies a bare `tofu … apply` and any `ansible-playbook` command naming a `site.yml`, its checks included. The rules match the command an agent writes, so wrapping one in `sops exec-env`, `bash -c` or a script to get past them breaks this rule as much as running it bare. A plan that needs arguments, such as `-replace`, is `go tool task --force <step>:plan -- <arguments>`, which `<step>:apply` then applies. The other OpenTofu commands (`show`, `providers lock`, `state`, `import`) and `maintenance.yml` plays run as before, each under rule 1 where it changes anything.

- Run plans from a root, never from a child module.
- Write plaintext plan output and saved plans to `docs/snapshot/`, each saved plan named for the commit it was made at, `<root>@<commit>.tfplan` (see [Parallel agents](#parallel-agents)). State and saved plans are AES-GCM encrypted with the passphrase from SOPS; never change or lose it.
- Apply exactly the saved plan Parker approved, then confirm a fresh plan is a no-op. The state bucket's versioning keeps every earlier state version, so applies need no separate backups.
- After an apply to `tofu/oracle` or `tofu/gonkputer`, run the next `ansible-generated` command with `--flush-cache`: its inventory caches their state for an hour.
- The `oci` CLI uses a session token, which lasts 60 minutes; refreshing extends it up to 24 hours. After that, Parker must run `oci session authenticate --profile-name DEFAULT` himself. OpenTofu needs no session. Each `oci` call needs `--auth security_token`, or `OCI_CLI_AUTH=security_token` in its environment; check WSL's environment for it first. `oci session validate --profile DEFAULT --local` says whether the session has expired.
- A root's `prepare.sh` is sourced by `tasks/tofu.sh`, inside that task's process alone, so no shell of the session needs it. Run gonkputer's tasks in the background, as the provider's SSH may wait on the agent. `sops exec-env` refuses a file with any map or list value, such as `nexus_servers.sops.yml`: read one value from it with `sops decrypt --extract`. The guard counts any command containing "git" as git: glob `.g?thub`, and grep `ithub\.`.

## Tasks

`Taskfile.yml` is the pipeline, run with go-task, which the root `go.mod` pins as a tool: `go tool task` builds and runs that version, after a first build of about a minute. It holds the steps and the order they run in, and is the only place that order is written down. A step is an OpenTofu root, in one workspace where the root has several (`stripe.live`), or an Ansible stage. `go tool task --list` lists every task with its description.

```bash
go tool task init                                    # every step's init, in order: a root's providers where it has none, a stage's collections where requirements.yml changed, and every step's signals
go tool task plan                                    # plan or check every step whose inputs changed, in order, past any that fails; then `go tool task pending` and the failed steps
go tool task pending                                 # the saved plans that show changes and wait to be applied
go tool task <step>:plan                             # one root: a saved plan, docs/snapshot/<step>@<commit>.tfplan
go tool task <step>:apply                            # one root: apply that plan, re-plan it, then plan or check its dependents
go tool task <stage>:check LIMIT=<hosts> TAGS=<tags> # part of a stage, --check; arguments after `--` go to ansible-playbook
go tool task <step>:references                       # what the step reads from other steps and roots, and in which file
go tool task <stage>:syntax                          # ansible-playbook --syntax-check of the stage's site.yml and maintenance.yml
go tool task <stage>:apply LIMIT=<hosts> TAGS=<tags> # part of a stage, or all of it without LIMIT and TAGS; then its dependents
```

- **Iterating:** while editing configuration, run any single step as often as helps: one root's plan, or a stage checked or applied on one host with `LIMIT` and `TAGS` ([Tagged applies](#conventions)). Before reporting the work done, run `go tool task plan`, and bring Parker every plan it leaves pending.
- **Signals:** each step records digests of what it exposes in `.task/signals/`, which is gitignored. A root records a digest of its outputs. A stage records a stamp that each apply rewrites. Before a step plans, checks or applies, `tasks/upstream.sh` collects the signals of everything the step reads into `.task/upstream/<step>`. It finds those reads in the step's own files: `terraform_remote_state` keys, `tf_output` lookups' `project_path`, other roots' SOPS files, and each `*.terraform_state.yml` inventory source. An inventory source's signal is a digest of what its plugin selects from the state, which is every attribute it makes a host variable. `tasks/inventory-digest.sh` has the plugin build that selection into a private cache made for the digest, so the signal follows the inventory file and no filter of ours restates it. A dependency that no file of the step names, such as `tofu/authentik`'s on `ansible-generated`, goes in its include's `EXTRA`. The signals are only digests: no output or state is written to disk in plaintext, and every consumer still reads the remote state itself.
- **Propagation:** a step's upstream file is one of its `sources`, so `go tool task plan` re-plans a step when its own files or anything upstream of it changed, and skips it otherwise. Every apply ends by propagating to its dependents, which `tasks/dependents.sh` finds from each step's `references`: it plans each OpenTofu step that reads the applied one, and checks each Ansible step that reads it, limited to the hosts or groups whose own vars do so, or the whole step where its `group_vars/all`, roles, playbooks or inventory sources do. A dependent whose plan or check shows changes needs its own apply, which propagates in turn, until every plan is empty. `go tool task plan` stays the closing pass over the whole pipeline. The pipeline has no cycles. A host that reads a root which itself needs that host's stage gets a step of its own after the root: the stage leaves it out (`EXCEPT`), and its own step covers it alone (`HOST`). memory, which reads `tofu/authentik`'s outputs, is handled this way. A step whose hosts need an agent of their own sets `WRAP`, a command of the stage's `bin` that each `ansible-playbook` runs inside: the SG300s are `ansible-hardware--switches`, run inside `bin/with-switch-keys`, which `ansible-hardware` leaves out (`EXCEPT: ciscosmb`).
- **Approvals:** `plan`, `pending`, `check` and `<step>:outputs` are read-only. Each `apply` is a mutation under rule 1: ask for that exact command, after its plan or check. `init` installs a root's providers wherever its `.terraform/` is missing, and a stage's collections wherever its `requirements.yml` changed or they are missing, each of which needs Parker's approval under rule 3; in a worktree, symlink them first ([Parallel agents](#parallel-agents)). A step's `outputs`, which every dependent's plan runs, refuses a root without providers rather than installing them. Moving go-task to another release (`go get -tool github.com/go-task/task/v3/cmd/task@<version>`) is an install too.
- **Costs:** a stage's `plan` is `site.yml --check` on every host, so `go tool task plan` runs it only when the stage's files or upstream changed. Its result is in the recap: a check leaves no pending marker. A stage's check opens a connection per fork at once, each signed through the operator's agent, so Parker approves the first prompt with Bitwarden's remember before the rest time out; the hosts that fail on `Authentication timeout` or `signing failed` are checked again once it is remembered. A step that fails does not stop `go tool task plan`, which names every failed step at the end and then fails. A clone or worktree with no `.task/` plans everything once. `go tool task --force <step>:plan` re-plans a step whose up-to-date check is wrong.
- **A new step:** add an include to `Taskfile.yml` and its place in `STEPS`.
- `tasks/tofu.sh` and `tasks/ansible.sh` run each command as [Everyday commands](#everyday-commands) describes: a root's own `prepare.sh`, sourced into that command's process alone; a stage from inside its folder, with the backend's credentials and `--flush-cache`; and alock's `PATH` fix.

## Reaching hosts by hand (read-only)

- One plain `ssh <host> <command>` each. In a worktree session the guard refuses a heredoc to `ssh`, so redirect a file: `ssh <host> sh -s < <file>`.
- To reach a host by its inventory name, pass `-o HostKeyAlias=<name> -o UserKnownHostsFile=<repository>/ansible-<stage>/known_hosts`, and never accept an unverified key.
- From WSL, `ssh aboriginal`, the tailnet alias, works where `aboriginal.regulad.internal` doesn't. WSL has no IPv6 route to the tailnet or the VCN, so test IPv6 from a host there, such as tailscalerouter.
- arawi logs in to csh: pipe it a POSIX script. `sudo -n` reads its root-only `/var/log/*.log`.
- The Arista takes several `show` commands in one quoted string, one per line.
- A container's journal: `ssh prodingus 'pct exec <vmid> -- journalctl …'`.
- overture needs `ssh -o RemoteCommand=none`, and Homebrew isn't on its non-interactive `PATH`.
- Orchard's API: write `orchard_controller_cert` to a temporary file with `sops decrypt --extract`, and give `curl --config - --cacert <cert>` the line `user = "bootstrap-admin:<token>"` on stdin.

## Parallel agents

Several agents may work on this repository at once. The [alock](https://github.com/regulad/alock) plugin, pinned in `.claude/settings.json` and configured by `.alock.json`, keeps their applies apart. While a `tofu`, `terraform` or `ansible-playbook` change runs, it locks the OpenTofu root with every host that root's inventory lists, or each host an Ansible run resolves to. It refuses an apply whose HEAD lacks the commit any of those targets was last applied from, so no apply undoes another. Read-only calls, such as `plan` and `--check`, pass straight through.

- **Worktree or main checkout:** when Parker asks for work, ask him whether to do it in a worktree of its own or in the main checkout; never assume either. A worktree lives at `.claude/worktrees/<name>` on a branch of the same name. It starts without the gitignored files: run its roots' `prepare.sh`, and symlink `ansible-*/collections/` and `tofu/*/.terraform/` from the main checkout rather than installing them again (rule 3). It starts without its submodules' contents too: check them out with `git submodule update --init`.
- **One worktree per agent.** Once an agent has its worktree, it creates no other unless Parker authorizes that one specifically; the work it is asked for next continues in the same worktree.
- **Pivots mid-iteration:** when Parker redirects an agent before its changes are ready to commit, suggest stashing them, do the new work in the same worktree, and apply the stash on returning. Every worktree and clone shares one stash list, so stash only your own paths under a unique message (`git stash push --include-untracked -m "<worktree>: <what>" -- <paths>`), note the entry's id from `git stash list --format='%H %gs'`, restore it with `git stash apply <id>`, never `pop`, and once it is applied drop the entry, found again by its message.
- **Apply from a commit.** alock refuses a worktree with uncommitted changes. In a worktree, commit on its branch first (rule 8's exception). In the main checkout, that commit lands on master, so Parker approves it along with the apply.
- **Only master is pushed.** origin holds one history, master's. A worktree's branch stays in this clone, where alock reads its commits, and its work reaches origin only when Parker merges it into master. This is the exception to regulad/skills' rule that an agent pushes its commits.
- **Saved plans** are made and applied at the same commit, and named for it: `docs/snapshot/<root>@<commit>.tfplan`, with at least seven characters of the commit. A root with workspaces, such as `tofu/stripe`, adds the workspace: `<root>.<workspace>@<commit>.tfplan`.
- **Run applies in the background** (`run_in_background`). alock waits up to 10 minutes for a held lock, longer than the Bash tool lets a foreground command run.
- **A lock that stays held** makes the change fail without running, naming its holder. Report that to Parker. If the holder is gone, message the other agents working on this repository, so a live one can object; then Parker runs `/alock:break -C <repository> <target>`. Agents never run it.
- **To roll a target back,** `git revert` the applied commit on a branch that contains it, and apply the revert. There is no other way to undo an apply.
- **After an apply moves a target's record forward,** other worktrees can't apply to that target until they contain the commit. Tell the other agents working on this repository, so they can rebase onto it.
- **`alock.mode` is Parker's:** `local`, in this clone's `.git/config`, as every agent applies from this one clone. Agents may read it, never change it.
- **A new OpenTofu root** goes into `.alock.json`, with the inventory listing the hosts it creates; alock refuses a root it doesn't list.
- **Unlocked:** ad hoc `ansible`, `pct`, `qm`, `ssh` and web interfaces bypass alock. Before changing a host one of those ways, check with Parker that no other agent is applying to it.
- **A pending fleet-wide check or apply holds exclusive control.** A peer that asks to go ahead waits until your apply is done or Parker releases it: its applies or git moves would shift alock's records under you.
- **alock's pin:** `.claude/settings.json` pins alock by `ref` and `sha` through an inline `settings` marketplace. `claude plugin` sees it only once a session in the trusted folder has registered it: run a minimal `claude -p`, then `claude plugin install alock@alock --scope project`. To move to another release, change `ref` and `sha` and reinstall. No fail-closed project hook backs it up, as one would be a point of failure of its own.
- **Until alock fixes it,** when `PATH` lists alock's `bin` twice, or two versions' `bin`, 0.2.0's shim finds a shim instead of `ansible-playbook` and spins at `--list-hosts`, running nothing and taking no lock. Prefix alock-wrapped commands with `export PATH="$HOME/.claude/plugins/cache/alock/alock/0.2.0/bin:$(printf '%s' "$PATH" | tr ':' '\n' | grep -v '/.claude/plugins/cache/alock/' | paste -sd:)"`, and check that a background apply's log grows. 0.2.1 doesn't fix it: its only change is the holder-file fix.

## Conventions

- **Docs:** `AGENTS.md`, `.claude/PLAN.md`, and every `README.md` contain only intent and current state. Record what happened as a new entry in `.claude/history/`, a file named `<date>.<slug>.md` as its README describes: a title saying what was done, and only the findings a later session could use, not approvals, apply counts or routine confirmations.
  - **An entry is committed with the work it records,** in that work's own commit, or in the last of its commits where it spans several. Only an entry that records no change to the repository, such as an investigation, is a `docs(history)` commit of its own.
  - **Its findings come from the apply,** which alock makes from a commit, so the entry is amended into that commit afterwards, before the branch is pushed or merged: `git commit --fixup=<commit>` with the entry, then `git rebase --autosquash` onto the branch's base. alock follows the rewrite.
  - **A change an apply shows the feature commit lacked,** as memory's `mail_relay_password` was, is a `fix(<scope>):` commit of its own, with a body saying what it adds and why. `--fixup` is only for amending a history entry into the commit it records.
- **Guest names:** lowercase, hyphenated, stable (`svc-<name>`, `host-<role>`); the tailnet MagicDNS name equals the hostname.
- **Tags:** every guest is marked as managed by OpenTofu: `managed-by=opentofu` on OCI instances, and the tag `terraform` on Proxmox guests, whose tags cannot contain `=`. Tailnet tags and their ACL groups are defined in `regulad/tailscale-acls`.
- **OS groups:** every host Ansible manages is in exactly one OS group, `debian`, `ubuntu`, `rhel` (Oracle Linux, Rocky and Alma), `freebsd` (pfSense) or `macos`, which roles such as `ca_trust` key their behaviour on through `group_vars/<os>.yml`. Generated hosts get it from OpenTofu: an `os` freeform tag on OCI instances, and the group in each Proxmox guest's `ansible_host`. Hardware hosts list it in `hardware.yml`.
- **OpenTofu:** one root per provider; modules take explicit inputs; no secrets in `locals`.
- **Ansible:** roles expose knobs in `defaults/` and avoid `vars/`; handlers for restarts; every role passes `ansible-lint`. Never merge, rename or restructure roles unasked. A feature that targets other hosts gets its own play; to share settings, offer `tasks_from` entry points (as clamav's `onaccess` and `scan`), a shared meta-dependency role or group_vars, and let Parker pick.
- **AIDE:** a role that writes on a Debian, Ubuntu or Enterprise Linux host lets AIDE's refresh take in what it writes, as [AIDE.md](AIDE.md) sets out: files through the modules the `aide_written` callback records, anything else a task writes declared in its `aide_writes`, and a service's runtime data excluded rather than declared.
- **systemd's own units:** a role favours the systemd-idiomatic way of doing a job, as units it renders from its data (`defaults/`, group_vars, host_vars), over writing a file that a generator or another daemon turns into that job: a mount is a `.mount` unit, not an `/etc/fstab` line, and a schedule a `.timer` and its service, as `restic_jobs` are, not a crontab entry. Pre-existing, and kept as they are: the `swap` role's fstab lines for disk swapfiles, the `matrix` role's `/etc/cron.d/synapse-auto-compressor`, livekit's `/etc/crontab` with certbot's renewal, and pterodactyl's root crontab with the panel's scheduler.
- **Ansible tags:** every task carries a tag, through the play that runs it: each play in a `site.yml` is tagged with the name of each role it applies, and a play that imports a role's `tasks_from` entry point is also tagged `<role>_<entry point>` (`clamav_scan`); each play in a `maintenance.yml` is tagged with the operation it runs. A new play gets its tags as it is added. Each stage's `site.yml` and `maintenance.yml` end by importing `ansible-common/playbooks/aide-refresh.yml`, whose play moves AIDE's baseline for the files the run wrote, then ends the hold on each host's daily check that the shared playbooks' first import, `aide-hold.yml`, put on at the run's start; both are also tagged `always`, so that a tagged run holds the check and refreshes what it wrote.
- **Tagged applies:** prefer them for their speed. A change is checked and applied with only its tags and the hosts it affects, `--tags <role> --limit <hosts>`, instead of a run of the whole `site.yml`, which goes through every play on every host, most of them containers reached task by task through `pct`. Facts are still gathered, because fact gathering runs under any `--tags`. Where a role relies on what an earlier play sets up, such as `quadlet` on `podman`, include that play's tag too.
- **pfSense:** the `pfsense` role converges `config.xml` through `pfsensible.core` modules wherever one works. Each part they cannot manage is a `pfsense_config_section` section, a template in `host_vars/<host>/config/` that replaces the elements it owns; paths something on the host rewrites are listed in its `ignore`. Every part of `config.xml` has one owner: when a module cannot model a field, the whole object type moves to a section rather than splitting ownership, and parts that pfSense or a package writes are left to them. Files outside `config.xml` come from `files/<host>/`. Each host pins its pfSense `<major>.<minor>` release in `pfsense_release`, because pfSense does not follow semantic versioning, and lists its packages in `pfsense_packages`; the role installs missing ones through pfSense's own installer and never removes any. The operator's `config.xml` snapshot is authoritative over the live file: a fix the role cannot make is edited into the snapshot, pushed over SSH, and applied through pfSense's PHP.
- **Encoded values:** where a system stores a value encoded, such as pfSense's base64 of a PEM certificate or of Kea's JSON, the repository keeps it readable and encodes it where it is rendered: `b64encode` in a template, or a module that encodes it itself. Diffs then show what changed. Convert an encoded value whenever the file holding it is edited; keep one encoded only where nothing can encode it at render time. Secrets stay in SOPS either way. For example, a pfSense section's Kea options, before:
  ```xml
  <custom_kea_config>ew0KICAiYWxsb2NhdG9yIjogInJhbmRvbSIsDQogICJvcHRpb24tZGF0YSI6IFsNCiAgICB7ICJuYW1lIjogImRvbWFpbi1uYW1lIiwgIm5ldmVyLXNlbmQiOiB0cnVlIH0NCiAgXQ0KfQ==</custom_kea_config>
  ```
  After:
  ```jinja
  {% set opt2_kea_config = {
    "allocator": "random",
    "option-data": [
      {"name": "domain-name", "never-send": true},
    ],
  } %}
  <custom_kea_config>{{ opt2_kea_config | to_json | b64encode }}</custom_kea_config>
  ```
  A certificate works the same way: its PEM in host_vars as a YAML literal block, and `<crt>{{ arawi_cert_crts[refid] | b64encode }}</crt>` in the section.
- **Ansible secrets:** SOPS-encrypted `host_vars/<host>/secrets.sops.yml` or `group_vars/<group>.sops.yml`; secrets both stages need live once, in `ansible-common/group_vars/all.sops.yml`, which each stage's `group_vars/all.sops.yml` symlinks. They are loaded by the `community.sops.sops` vars plugin each stage enables in its `ansible.cfg`; never Ansible Vault or decrypted copies on disk. Plaintext vars reference secrets by name, and tasks that pass them set `no_log: true`.
- **SSH connections:** Ansible reads no SSH configuration, the operator's or the system's: each stage's `group_vars/all.yml` passes OpenSSH `-F /dev/null`, so every host connects from what its inventory declares alone, its full hostname and its `ansible_user`, from any controller. A hardware host is named by its full hostname; a generated host's `ansible_host` is its full one.
- **SSH host keys:** each stage's `known_hosts` holds the host keys of the hosts it reaches over OpenSSH, under their inventory names. Its `group_vars/all.yml` makes that file the only one OpenSSH reads, with strict checking, so a missing or changed key fails the connection. A new or rebuilt host's key goes into the file in the change that creates or rebuilds it, read from a source that authenticates it, such as FreeIPA's record of the host or a scan whose route stays inside the tailnet, never accepted on first use. The switches' libssh and `proxmox_pct_remote`'s paramiko still read `~/.ssh/known_hosts`: neither plugin can be given another file.
- **Generated secrets:** every random value generated for the homelab, such as a password, shared secret or key, records its provenance in a comment directly above its key in the SOPS file, which SOPS encrypts with it: the date, the generator and its parameters, and the resulting length and alphabet. For example, `# Generated 2026-10-27: 32 characters of [A-Za-z0-9], each from Python's secrets.choice.`
- **Keys per task:** a new host, or a new task that authenticates to an API, gets a key made for that task alone, with the narrowest access that serves it, never a copy of a key another task holds. regubot's are the pattern: each of its tokens serves one pipeline or root (`terraform-github--user`, `terraform-jenkins--winget`), and Jenkins's winget jobs sign with a key of their own, as each host's B2 application key is its own. One task's key is then revoked or rotated without touching another's. In particular, no new resource uses `id_rsa3072`, regulad's own SSH key (`tofu/shared`'s `regulad_ssh_public_key`): it stays only where it is already registered, and anything new gets a key of its own. A shared secret that only opens what every holder already shares, such as the restic password, stays one (see No security theatre).
- **Quadlets:** one file per unit, rendered by the `quadlet` role from `host_vars/<host>/services.yml`, with secret env files in SOPS; volumes named, not bind-mounted from ad hoc paths; shared data on the container's CephFS mount (`/mnt/cephfs`) is bind-mounted from there. Images preferably track a major-version tag (or a release channel such as vaultwarden's `testing`) with `AutoUpdate=registry`, so `podman-auto-update` brings in patch and minor releases and containers get patches the same way as the system they run on, through its automatic updater. `latest` is used only where upstream publishes no version or channel tag besides dated or per-commit builds, as for timemachine and tvheadend. Hosts not already on Podman keep their current runtime. Containers run read-only, the `quadlet` role's default, with a `tmpfs` for any path outside its volumes that the image writes; one whose image must write its own root sets `read_only: false` and says why.
- **File names:** where `-` delimits parts of a file name (`instance-<name>.tf`, `subnet-<name>.tf`, `vm-<name>.tf`, `lxc-<name>.tf`), write each `-` inside a part as `--`. For example, subnet `subnet-20230331-2242` lives in `subnet-subnet--20230331--2242.tf`, and VM `resolute-template` in `vm-resolute--template.tf`.

### OpenTofu HCL (as practiced in `tofu/oracle`)
- **HCL first:** ordinary, readable `.tf` resources with inline non-sensitive settings and direct references. SOPS holds sensitive input values only, never encrypted HCL, resource definitions, or a topology data model.
- **Files:** a root is one flat module, since OpenTofu loads no subdirectories into a module; file-name prefixes group its files. One `instance-<name>.tf` per host and one `subnet-<name>.tf` per subnet, each opening with a `# <name>: <contents>.` header. Each VCN's `network-<vcn>.tf` holds its own `locals`, the VCN, gateways, and the defaults the provider creates with the VCN. A distinct concern gets its own file (`email.tf`, `state-bucket.tf`). `locals.tf` holds only values shared across files, and `variables.tf` declares inputs. `moved.tf` keeps every past address move so old states and backups still plan cleanly.
- **Order within a file:** file-local `locals` first, then the primary resource, then what depends on it.
  - Host files: instance, boot volume, backup-policy assignment, each data volume with its attachment and backup-policy assignment, VNIC lookup, IPv6 assignment, NSG, NSG rules.
  - Subnet files: the subnet, then its own DHCP options, route table, and security lists.
  - `network-<vcn>.tf`: VCN, internet gateway, DHCP options, route tables, security lists.
- **Order within a resource:** meta-arguments (`for_each`) first, followed by a blank line. Then identity (`display_name`, `compartment_id`, parent IDs), placement (`availability_domain`, `fault_domain`), other scalar arguments, and nested blocks. Blank lines separate nested blocks; none directly inside an opening brace. Keep list order the provider or service treats as meaningful.
- **Imperative leftovers:** every adopted resource ends with this footer:
  ```hcl
    # The following exists as an artifact of import from the imperative setup.
    lifecycle {
      prevent_destroy = true
    }
  ```
  Schema placeholders that exist only for adoption, such as the boot-volume `source_details { type = "bootVolume" }`, sit between that comment and `lifecycle`. `ignore_changes` stays as narrow as possible and carries a comment explaining what owns the ignored field. Image-created boot volumes ignore only `source_details`; never fabricate a clone or restore source.
- **Opaque values get a comment:** wherever possible, put a comment next to any value whose meaning is not self-evident:
  - protocol numbers: `"1" # ICMP`, `"6" # TCP`, `"17" # UDP`, `"58" # ICMPv6`, `"all" # All IP protocols`
  - ICMP `type`/`code` pairs: `type = 3 # Destination Unreachable`
  - ports, on the opening line of the block holding `max`/`min`: `destination_port_range { # SMTP`, `tcp_options { # SSH`. A rule whose existing `description` already names the port needs no comment.

  Plaintext Oracle OCIDs need no comment: their map key is their exact name (rule 4).

  Use HCL comments for this, not new `description` arguments; adding a description changes infrastructure.
- **IPv4/IPv6 pairs:** values that exist per IP family are objects keyed `ipv4`, then `ipv6`, named `dual_stack_<what>` when local (`local.dual_stack_internet_cidrs`, `module.shared.tailscale_cidrs`, `var.router_next_hop_ids`).
  - Rules or routes identical across families iterate over the pair: `for_each` with `each.value`, or a `dynamic` block with `iterator = cidr`. The stable family keys keep resource addresses independent of ordering.
  - Rules that differ by family stay explicit.
  - A shared address pair never implies a permission for both families. Comment any family-only exception, such as an IPv4-only peering rule.
  - Constants that belong to one subnet or host live at the top of that file; a VCN's pairs live in its `network-<vcn>.tf`, and pairs several files use in `locals.tf`.
- **Addresses:** GUA host addresses are `cidrhost(var.ipv6_subnet_cidrs.<vcn>, parseint("<64-bit hex suffix>", 16))`. Enclosing prefixes are derived from the encrypted `/64`, never written.
- **Lookups:** read a host's VNIC through a `data "oci_core_vnic_attachments"` filtered to `ATTACHED` and `one()`, so a second VNIC fails loudly instead of being guessed.
- **Inputs:** sensitive inputs are `sensitive = true` and `nullable = false` and come from `secrets.sops.json`. Non-sensitive values are inline HCL, not variables. Resource-free constants shared by several roots live in `tofu/shared`.
- **Versions:** pins live only in each root's `versions.tf`. OpenTofu's own version is its `language { compatible_with { opentofu } }` block, since OpenTofu ignores `required_version` in `.tf` files. Child modules declare provider sources only and start with `# tflint-ignore-file: terraform_required_version, terraform_required_providers`.
- **Tags:** every OCI instance sets `freeform_tags = { "managed-by" = "opentofu", "os" = "<os group>" }` as its last scalar argument.
- **Deferred problems:** a setting known to be wrong but kept for now gets `# FIXME(#N): <what is wrong>. Revisit <when>.`, naming the issue that tracks it, on the lines directly above it.
- **Labels:** resource labels are stable identities; renaming one needs a `moved` block. NSG rules are labelled `<host>_<protocol>_<port or range>`; bailout's two family-specific rules keep their adopted `bailout_rule_NN` labels.

### Proxmox HCL (as practiced in `tofu/gonkputer`)
The rules above apply, with these additions.
- **Resource names:** use the short `proxmox_*` names. The long `proxmox_virtual_environment_*` names are deprecated; use one only where no short name exists yet (containers, firewalls, DNS/hosts/time, users/groups/roles, files). VMs stay on `proxmox_virtual_environment_vm`: the short `proxmox_vm` is a different resource, the experimental former `vm2`, which the provider marks unfit for production.
- **Files:** one `vm-<name>.tf` or `lxc-<name>.tf` per guest, holding the guest, then its HA resource and firewall resources. Cluster-wide concerns get their own files (`cluster.tf`, `firewall.tf`, `ha.tf`, `storage.tf`, `mappings.tf`, `backup.tf`, `access.tf`, `snippets.tf`). Labels are the guest name with `-` written as `_`.
- **References:** VMs reference the custom CPU model's `cputype` and hardware mappings by name; HA resources reference their guest's `vm_id`; HA rules reference HA resources. Snippet volume IDs stay literal, because `vendor_data_file_id` forces replacement and a file still to be created is unknown at plan time; the guest lists the file resource in `depends_on`.
- **Defaults:** where a setting is unset live and the provider's default differs from Proxmox's effective value, write Proxmox's value explicitly with a comment. Never hide such a diff with `ignore_changes`. Compare against the provider's source and Proxmox's API schema, and let the plan confirm.
- **Generated values stay out:** guests don't state `vm_id`, and disks don't state `path_in_datastore` or `file_format`. Proxmox generated them, and state tracks them since adoption, as with OCIDs. Anything that needs a guest's ID references its `vm_id`.
- **New containers** start from `tofu/gonkputer/lxc-TEMPLATE.tf.example`, a skeleton with the shared defaults (Ceph root disk with discard and lazytime, DHCP and SLAAC on VLAN 1, effectively unlimited swap, nesting, an HA resource and the Ansible host): copy it to `lxc-<name>.tf` and fill in its placeholders.
- **Guest firewalls:** every guest has its firewall configured in its own file: `firewall = true` on its NICs, `proxmox_virtual_environment_firewall_options` enabling the firewall with an input policy of `DROP`, and `proxmox_virtual_environment_firewall_rules` admitting only what the guest serves, each port commented as above. A guest that a firewall would break, such as softether, whose hub bridges VPN clients through its NIC, or a router such as arawi, has no firewall at all, as dodo and aboriginal have none: `firewall = false` on its NICs, with the reason beside them, and no firewall rules or options of its own.
- **Container CPUs:** every container sets `cores = local.cpu_threads` (the node's 32 logical CPUs) and caps CPU time with `limit`. Proxmox would treat a missing `cores` as every core, but the provider cannot leave it unset: it reads a missing `cores` as 1 and sends 1 on any `cpu` change.
- **Ansible inventory:** each guest file that Ansible manages (containers, and VMs that cannot use cloud-init) ends with an `ansible_host` whose `count` is 1 while the guest is requested (a started HA resource, or no HA resource and starting on boot), named `<name>.${local.guest_domain}`. `ansible-generated` reads these from state, and reaches containers through `proxmox_pct_remote`. VMs that boot with cloud-init, or are being moved to it, get no `ansible_host`; their vendor file configures them.
- **VMIDs:** the cluster's `next_id` starts at 200, so guests created from here on are set apart from the adopted ones below it.
- **No `protection` flag:** a guest OpenTofu manages carries no Proxmox `protection` flag. `prevent_destroy` guards it, and the flag refuses even a drive's detach.
- **Tags:** every guest lists `terraform` among its `tags`, sorted as Proxmox stores them, as its last scalar argument. Markers such as `amd64v3` are tags, not descriptions. Tag names live once, in `local.tags` in `locals.tf`; guests reference them (`local.tags.terraform`) instead of writing the string.
- **Opaque values:** PCI and USB vendor/device IDs get the device name as a comment (`id = "8086:2723" # Intel Wi-Fi 6 AX200`), as do other opaque IDs.

## Standing decisions

- **Pre-commit:** `.pre-commit-config.yaml` runs the pinned `pre-commit/pre-commit-hooks` plus local hooks that use installed tools (`language: unsupported`) or `pygrep`. Gitleaks is not wanted.
- **Discovery snapshots** stay on the operator's machine; only configuration derived from them is committed. Parker's review of `docs/snapshot/SUMMARY.md` gates the adoption phases.
- **OCI auth:** OpenTofu authenticates as Parker's own user with an API signing key. The key, its fingerprint and his user OCID are in `tofu/oracle/provider.sops.env`, which `prepare.sh` exports, as gonkputer's API token is. A session token lasts at most a day, and the key lasts until Parker deletes it from his user in the console, which revokes it. A separate scoped user would contain nothing, because `tofu/oracle` manages IAM policies itself. The `oci` CLI keeps a read/write session token in the `DEFAULT` profile.
- **OCI adoption is complete** for the scope in the OCI part of the plan's Phase 3. Never regenerate or re-import it.
- **OCI state** is remote: OpenTofu's s3 backend stores it in the versioned `homelab-tofu-state` bucket through OCI's S3 Compatibility API, with S3-native locking (`use_lockfile`, verified against OCI). It is encrypted client-side with AES-GCM before upload. The backend authenticates as `svc-tofu-state`, whose customer secret key and endpoint are in `tofu/shared/backend.sops.env`. That key is created outside OpenTofu, never in state.
- **VCN defaults** stay ordinary adopted resources guarded by `prevent_destroy`. Moving them to `oci_core_default_*` resource types is wontfix.
- **Ansible scope:** each stage's main playbook is `playbooks/site.yml`, which imports `ansible-common/playbooks/site.yml` first. Every play in it converges hosts to the state declared here and is safe to rerun; a second run reports `changed=0`. Package updates come from each host's own automatic updater (unattended-upgrades, dnf-automatic) and containers' `podman-auto-update`, not from a playbook. Maintenance that cannot be automated, such as upgrading the Pterodactyl panel to its declared version by its documented procedure, lives in the stage's one other playbook, `playbooks/maintenance.yml`, one play per task, each tagged and run by hand. A Proxmox container's Ubuntu release upgrade, to the `ubuntu_release` its host_vars declare, is `ansible-generated`'s `release-upgrade` play, which snapshots the container on its node first. Other deliberate operations, such as rolling reboots, key rotation and restores, are not Ansible playbooks. Moving a service is a `host_vars` edit plus a `site.yml` run; its data moves by hand.
- **First pass describes; later passes prescribe.** A root's first adoption pass mirrors the live configuration exactly, warts included (for example an HA rule naming a node that had left the cluster). Fixes follow as separate, reviewed changes.
- **Adopted hosts are checked one by one.** Only the gonkputer guests at VMID 200 and above, and the OCI instances pihole2 and riko, were created from this repository, so one of each kind may stand for the rest. The hosts set up by hand and then adopted (the gonkputer guests below 200, the other OCI instances, the hardware hosts) may carry changes nobody declared: check each on its own.
- **gonkputer ownership:** node-level settings (network, DNS, hosts, time, APT, node options) belong to Ansible. Users and groups belong to the LDAP realm `home.arpa` and its sync. Ceph health warnings are known and can be ignored.
- **gonkputer API endpoint:** the node's tailnet name on port 8006, published by `tailscale serve` (tailnet only) with a Tailscale-managed certificate. Keep provider TLS verification on. The endpoint and token live in `tofu/gonkputer/provider.sops.env`.
- **gonkputer root tickets:** the provider sets `ssh.root_ticket`, so its calls under `/nodes/{node}/` run as `root@pam` with a ticket minted over its SSH connection to the node, bypassing the token's permissions. Proxmox reserves some operations, such as USB passthrough by device ID, for `root@pam` itself. Calls outside `/nodes/` still use the API token, so the token stays. Every plan and apply opens that SSH connection.
- **Provider mirror:** `tofu/gonkputer` pins a release of `bpg/proxmox` from the OpenTofu registry, and `tofu/github-user` pins a mirror build of `integrations/github`. Each root's `tofu.rc`, selected by sourcing its `prepare.sh`, lists `direct {}` before the mirror that [`regulad/opentofu-registry`](https://github.com/regulad/opentofu-registry) serves at `https://opentofu.regulad.xyz/`, which offers a build under the official address when the root pins one. Lock such a build with `tofu providers lock -net-mirror=https://opentofu.regulad.xyz/`. Provider development is out of band: homelab's docs never mention upstream PRs, fork branches or the provider's plans, though a code comment may link an upstream issue that explains a workaround. Ask Parker before moving the pin, or moving to a custom build.
- **Snippets:** hookscripts and cloud-init vendor files live byte for byte under `tofu/gonkputer/snippets/<storage>/`, uploaded by `proxmox_virtual_environment_file` over SSH as root through the operator's agent. They are created over the live files, not imported, and are exempt from the whitespace hook.
- **Ceph scope:** `tofu/gonkputer` manages the Ceph objects created through Proxmox: the pools `rbd_ssd` and `rbd_cmr` (`proxmox_ceph_pool`) with their storages `rbd` and `rbd_cmr` (`proxmox_storage_rbd`), the CephFS `cephfs` with its pools (`proxmox_ceph_fs`) and its storage (`proxmox_storage_cephfs`), and the MDS daemons (`proxmox_ceph_mds`): `prodingus`, which serves `cephfs`, and the hot spares `prodingus1` and `prodingus2` on the same host. Storages are always separate resources, never created as a side effect of a pool or filesystem; `rbd_cmr`'s storage, which Proxmox's "Add as storage" made, is imported like any other. Destroying a CephFS is a manual procedure the provider refuses to run. The RADOS Gateway is Ansible's, through `ansible-hardware`'s `ceph_rgw` role on prodingus: its instance's `ceph.conf` section, its options in Ceph's configuration database, its users with their S3 keys (`rgw_keys`, in the shared `all.sops.yml`, which their consumers read too) and its buckets with their ACLs and policies. Not managed: `.mgr` and the RGW pools, which were not created through Proxmox; and monitors, managers, OSDs, Ceph configuration and CRUSH rules, which have no resources.
- **Privileged containers run without AppArmor.** Every gonkputer container that does not set `unprivileged = true` (immich, ncsusplitt, qb, timemachine, tsexit, tvheadend) must have AppArmor removed inside the guest, or it breaks; `ansible-generated`'s `lxc_guest` role purges it from any container whose user IDs map to themselves. Never install or enable AppArmor in one; unprivileged containers keep it.
- **AppArmor keeps no policy cache.** On every host with AppArmor, the `aide` role sets `skip-cache` in `/etc/apparmor/parser.conf` and removes `/var/cache/apparmor`, so each profile is compiled from its source in `/etc/apparmor.d`, which AIDE watches, at every load. The compiled cache would otherwise be loaded at boot in place of the sources, and AIDE cannot watch it: it does not walk into `/var/cache`, which it excludes, whatever a deeper rule selects (tested on AIDE 0.18.6 and 0.19.2). With `skip-cache` every load is a cache miss and nothing is written; as the boot script still asks for `--write-cache`, each profile logs "Failed to create cache" at every load, which is expected. `parser.conf` is a dpkg conffile, so an AppArmor update that changes it waits as a conffile prompt, which unattended-upgrades skips and logs; resolve it by hand, keeping `skip-cache`, then run `site.yml --tags aide` on the host. snapd compiles its snaps' profiles with a parser of its own, which `skip-cache` does not reach, and `snapd.apparmor.service` loads them at each boot from the cache it writes there; so on a host with snapd, `/var/cache/apparmor` is instead a tmpfs, the `aide` role's `var-cache-apparmor.mount`, and no cache outlives a boot: at each boot snapd compiles every snap's profile from its source in `/var/lib/snapd/apparmor/profiles`, which AIDE watches.
- **AIDE on Enterprise Linux keeps the package's rule for `/etc`.** On the rhel hosts (bailout, livekit, mail and tailscalerouter on Oracle Linux 9, wako on AlmaLinux 10), the package's `/etc/aide.conf` selects `/etc PERMS`: permissions, owner, group, ACL, SELinux label, xattrs and type, not contents. Only the files and trees it names, about 120 such as `/etc/ssh/sshd_config`, `/etc/sudoers`, `/etc/passwd`, `/etc/fstab`, `/etc/crontab`, `/etc/pam.d` and `/etc/systemd`, get a content rule, so a rewrite of any other file in `/etc` never appears in a report there. The gap is accepted; the role adds only exclusions to the package's rules. `aide -p f:<path>` shows the rule a path gets.
- **AIDE leaves `/boot` to Secure Boot where it is on.** aide-report reads the firmware's Secure Boot variable at each run and, while it is on, excludes `/boot` (`aide_exclude_paths_secure_boot`): on prodingus, aboriginal and dodo. With shim and GRUB, Secure Boot verifies the boot loader and the kernels, not the initramfs images, `grub.cfg`, `grubenv` or the boot entries, which go unwatched there; the gap is accepted. The other hosts with their own kernel keep `/boot` watched: vkasm boots by BIOS, and the OCI instances cannot have Secure Boot, as Shielded instances support neither VM.Standard.E2.1.Micro nor VM.Standard.A1.Flex and are chosen only at launch.
- **auditd's records stay on each host,** where they are read: forwarding them off-host is not wanted, nor exclusions for periodic pollers. The logs keep at most 10% of the root filesystem. Auditing from boot, `audit=1 audit_backlog_limit=8192`, is `kernel_params`' set `99-audit`: a GRUB drop-in on Debian and Ubuntu, and `grubby`'s arguments on every boot entry on Enterprise Linux. It takes effect at each host's next boot, which nothing schedules.
- **ClamAV on prodingus scans only prodingus's own filesystems.** Never scan containers' roots from the host (`/proc/<pid>/root`, `pct mount`, host-side fanotify marks): a container's coverage comes from inside it, or from where its files enter.
- **mDNS is systemd-resolved's, except where Avahi must reflect it.** Every homelab host with resolved resolves mDNS through it and answers it for its own name (`resolved` role): resolved is the host's resolver, and in a Proxmox container its stub replaces the `resolv.conf` Proxmox writes. Where NetworkManager manages the links, as on Enterprise Linux, it is kept out of DNS (`dns=none`), as its plugin for resolved would pass on every link's own servers, and the links take resolved's global settings; RHEL supports resolved from 10.0. resolved is preferred to Avahi for two reasons: it converges on systemd, and many programs, such as Go's and Rust's resolvers, skip NSS and query the nameserver in `resolv.conf` directly, which resolves `.local` names only when that nameserver is resolved's stub. Where a host's containers sit on Podman bridges, Avahi reflects mDNS between them and the LAN and resolves `.local` names through `nss-mdns`; resolved still resolves every other name there, with its own mDNS off. The Proxmox nodes, which run no resolved, answer for their names by Avahi alone, reflecting nothing. The OCI instances' networks carry no multicast and take no part.
- **VM 100 is never rebooted on its own.** Its passed-through AMD GPU does not reset properly when the KVM host detaches and re-attaches it, so the VM is restarted by rerooting, or together with a host reboot. It sets `reboot_after_update = false`; a change that needs a reboot stays pending until then.
- **kdump hosts panic on a hung task.** The `kdump` role sets `kernel.hung_task_panic=1`, so a task in D state for 120 s panics the host. Before killing or stopping anything that holds a dead device on one, tell Parker it can panic the host, not just hang a process.
- **Swap:** every Debian and Ubuntu host with its own kernel swaps to zram through systemd-zram-generator, at half its RAM (on prodingus, half of what the VMs' 1 GiB hugepages leave). Disk swap exists only on storage backed by a real drive: OCI boot volumes, prodingus's own disks, and the SATA SSDs passed straight into aboriginal and dodo. Never put swap on Ceph RBD. The OCI instances' swapfiles stay as they are.
- **Backups:** restic jobs are systemd services and timers from the `restic` role (`restic_jobs`), never cron. Hosts with btrfs back up from read-only snapshots; prodingus, on ext4, backs up its live root. aboriginal's `restic-forget` is the repository's only forget and prune, with a policy per tag; a tag no policy names, such as `nas`, is never forgotten.
- **Cross-site replication covers pihole2 and riko only.** Declined, and not to be raised again unless Parker asks: SRV records for riko, a replication write test, and replicas of Uptime Kuma, the exit node and clamd.
- **gonkputer firewall bypass:** VMs 100 (aboriginal), 101 (dodo) and 108 (arawi), and the containers softether and tailscalerouter, deliberately bypass the firewall (`firewall = false` on their NICs).
- **LAN-by-source rules** (`10.23.0.0/20`, `fd83:b84c:aa57:1::/64`) need no exclusions for arawi's NAT of INTERCOM, GUEST and LAN2, or for the Verizon router's hairpin: those VLANs aren't part of the risk profile. Tailnet clients keep their own addresses (SNAT off), so they don't match.
- **gonkputer state** lives in the same `homelab-tofu-state` bucket under the key `gonkputer/terraform.tfstate`, with the same backend credentials and its own encryption passphrase. No state from the draft carried over; all 86 resources were imported afresh, and the import blocks removed after the adoption apply.
- **backblaze state** lives in the same bucket under `backblaze/terraform.tfstate`, with its own passphrase. The root holds the whole B2 account: its buckets and application keys. The provider authenticates with the account's master application key, from `tofu/backblaze/provider.sops.env`, which never leaves the operator's machine. It runs before both Ansible stages: the `restic` role reads its `restic` output, the repository and a key per host, through the `cloud.terraform.tf_output` lookup. A host's key rotates with `tofu apply -replace` and then `site.yml`.
- **Nexus's addresses:** clients reach Nexus at `repo.regulad.xyz`, each repository at its path there, `/repository/<name>/`. A host of its own that serves one repository's path at its root, which Caddy on ingress gives `cr.regulad.xyz` (the `cr` Docker repository), `docker-cr.regulad.xyz` and `ghcr-cr.regulad.xyz` (the `docker-io` and `ghcr-io` proxies) and `ios.regulad.xyz` (the `ios` APT repository, with Cydia's flat files), is used only where a package manager cannot be pointed at that deeper path. Docker's API is one such: it always starts at `<host>/v2/`. A new repository gets one only for such a client, and anything that can take the path uses `repo.regulad.xyz`.
- **Restic password:** one repository password, shared by every host, in `ansible-common/group_vars/all.sops.yml` (see No security theatre). To rotate it, run `maintenance.yml --tags restic-password` once from either stage, then `site.yml` in both stages, then `--tags restic-password-prune`, which removes the old repository key.
- **Enrollment secrets are host state.** A secret a host gets by enrolling with an outside service, such as ncsusplitt's Duo device secret, is made and written on the host by a `maintenance.yml` play and kept nowhere else: never in SOPS or delivered by `site.yml`, even if it never changes. Recovery is a new enrollment. SOPS holds the secrets we choose or generate.
- **sudo through the SSH agent.** A user that Ansible or the operator logs in as and sudoes from authenticates that sudo with the operator's forwarded agent, through the `pam_rssh` role, wherever the host's sudo can: sudo 1.9.10 or later, for the `noninteractive_auth` that Ansible's `sudo -n` needs, with a build of pam_rssh in Nexus for its release. NOPASSWD stays only where it cannot: the base role writes the admin's where `pam_rssh_enabled` is off, and arawi keeps its `sudo.xml` rule, as pfSense has no pam_rssh. Ansible forwards the agent to the hosts that enable it, and to the Macs, whose sudo dotfiles puts through pam_rssh; each become is one signature, whose approval Bitwarden remembers. FreeIPA's `Admins` sudo rule carries no `!authenticate` (wako's `freeipa_server_sudorule_options_absent`), so SSSD brings no NOPASSWD back on the FreeIPA servers, riko and wako. aboriginal's and overture's sudo are dotfiles'. On Debian and Ubuntu `/etc/pam.d/sudo` is a dpkg conffile, so a sudo update that changes it waits as a conffile prompt, which unattended-upgrades skips and logs; resolve it by hand, keeping the pam_rssh line, then run `site.yml --tags pam_rssh` on the host.
- **Alexa skills:** each skill's package in `alexa/<skill>/` is its source of truth, as the ASK CLI lays one out; no tool tracks a skill's state. Drift shows by exporting the live package (`ask smapi export-package`) and diffing; a change is `ask deploy --target skill-metadata` from the skill's directory. The ASK CLI comes from `regulad/dotfiles`, signed in per machine with `ask configure` and never linked to AWS. A skill's AWS side, such as the Smart Home skill's Lambda, belongs to `tofu/aws`. Use the ASK CLI's default profile: `--profile __ENVIRONMENT_ASK_PROFILE__` forces telemetry on. Never print `~/.ask/cli_config`, which holds the refresh token, and never run `ask smapi get-skill-credentials` in a session.
- **GitHub secrets:** `tofu/github` sets the Actions, Dependabot and environment secrets of regulad's and regubot's repositories, each account's in a workspace of its own, `personal` and `bot`. It also defines the environments that another root's credentials trust, such as Warlock's, which `tofu/azure`'s federated credentials let sign. Only repositories that need secrets are defined there; a repository with no secrets is not defined in policy. In each workspace OpenTofu authenticates as that account's own GitHub App, installed on all of the account's repositories, so a repository's first secret needs only its definition there. Every value is derived: from SOPS, from another source in this repository, or as a plaintext literal where it is no secret. Personal access tokens stay hand-issued, in their account's SOPS file in `tofu/github-user`, until workflows move to App-issued tokens; that later flow is to use GitHub's built-in tokens wherever they suffice and an App of its own for each repository otherwise.
